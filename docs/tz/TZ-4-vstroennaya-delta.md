## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Встроенная дельта** | Наши правки **внутри** кода вендора, которые нельзя заменить вызовом своего модуля: новый параметр функции вендора, изменённое выражение, вставка в середину запроса. Остаются в коде вендора и переносятся на новую версию слиянием git. |
| **Метка ШХ, точка дельты** | Пометка в коде вендора: «здесь наша правка». Формат `// ШХ <ID>`. Одна метка — одно место. Единица учёта в метриках. |
| **ID метки** | Номер позиции реестра + порядковый номер: `07-03` = позиция 7, третье место. По ID место находится и в коде, и в таблице 3 реестра. |
| **Сигнатура функции** | Имя функции и список её параметров. Если мы добавили параметр (поз. 7: `ЕдИзм`; поз. 8, 13: `Договор1С`), то **новые** вызовы, которые вендор добавит в следующей версии, этот параметр не передадут. Это ловит сигнатурный контроль ТЗ-5. |
| **Контекст договора** | Возможная замена сквозного параметра `Договор1С`: договор запоминается в переменной модуля в начале обработки документа, функции чтения настроек берут его оттуда, в конце — сбрасывается. Меток становится 3–5 вместо ≈20. |
| **«Протекание» контекста** | Ошибка, при которой договор от предыдущего документа остаётся в переменной и применяется к следующему. Главный риск варианта «контекст договора». |
| **Мёртвая дельта** | Наша правка, которую вендор в новой версии сделал сам. Её можно удалить. |

## 1. Зачем это и что делаем (суть простыми словами)

После ТЗ-3 большая часть нашего кода уже вне вендора. Остаются места, где вынести нельзя: например, мы добавили параметр в функцию вендора, и все вызовы этой функции передают нам договор. Такие правки должны жить внутри кода вендора.

Задача шага — сделать этот остаток **минимальным, размеченным и проверяемым**:

1. **Минимальным** — всё, что длиннее 3 строк и выносится вызовом, уходит в `т1кДиадокМодули`. По позициям 7 и 8+13 исследуем, можно ли вообще обойтись без правок вендора.
2. **Размеченным** — каждое место получает метку `// ШХ <ID>` и строку в таблице 3 реестра: где, что, зачем, автор, как проверить. Старый разнобой (`// + ШХ`, `// - ШХ`, ссылки на карточки т1к) в этих местах заменяется на метки; автор, дата и задача переносятся в реестр.
3. **Проверяемым** — по каждой метке понятно, какая проверка ТЗ-5 или ТЗ-2 её контролирует.

Отличие от плана v1: размечаются **только точки дельты** (десятки мест), а не все 205 блоков. Блоки, ушедшие в основную конфигурацию, размечать не нужно — их нет в коде вендора.

## 2. Что разработать

### 2.1. Формат меток

```bsl
<код>  // ШХ 07-03            — правка в одной строке
// ШХ 08-05 {                — начало правки из нескольких строк
<код>
// ШХ 08-05 }                — конец
// ШХ 04-01 удалено: <исходная строка вендора>   — если мы убрали строку вендора
```
Вне меток слова `ШХ` в файлах вендора быть не должно (проверяет ТЗ-5, Б1).

### 2.3. Сокращение вставок
Любая вставка длиннее 3 строк, которую можно заменить вызовом `т1кДиадокМодули`, переносится туда. В коде вендора остаются только выражения, которые нельзя отделить: параметры вызовов, изменённые присваивания, условия в запросах.

### 2.4. Таблица 3 реестра
Для каждой метки: ID, файл, функция, что сделано, автор / дата / задача (из старых комментариев), как проверить (X1–X6, Б1–Б5 или smoke).

## 3. Как использовать

- **При конфликте слияния** на новой версии: по ID метки в таблице 3 видно, зачем правка и как её проверить. Смысл правки переносится на новый код вендора.
- **Новая доработка**, которую нельзя сделать событием ПМ или нашим модулем: метка с новым ID + строка в таблице 3 + правило проверки. Без строки в таблице проверка Б1 не пропустит.

## 6. Критерии приёмки

1. Каждое наше место в коде вендора имеет метку с ID и строку в таблице 3; каждая строка таблицы 3 найдена в коде.
2. Решения по §2.2 приняты и записаны (или явно отложены с пометкой «оставлено как есть»).
3. Компиляция и эталоны X1–X6 — без расхождений.
4. Объём оставшейся дельты (строк добавлено/удалено по сравнению с `vendor`) записан в реестр — это база для метрик.
