## 1. Зачем [План: шаг 3, «Зачем»]

Вся наша логика должна жить там, где обновление вендора её не трогает: в основной конфигурации, рядом с уже существующими `т1к*` (my-FT Т-3, Т-7, Р-1). В расширении (ТЗ-4) останутся только зацепки, которые эту логику вызывают.

## 3. Где лежит код в репозитории [План: §2 «Наш код в основной конфигурации»]

| Путь | Что |
|---|---|
| `SRC/main/` | выгрузка **наших** объектов основной конфигурации (только их, не всей ERP): ПМ, роль `шхДиадок`, общие модули `т1кДиадок*`, регистры `т1кДиадок_НастройкиДоговоров`, `т1кЗначенияПроизвольныхПараметров` |
| `SRC/main/objects.txt` | список этих объектов — по нему делается частичная выгрузка |

Источник истины для нашего кода — **база** (основная конфигурация); `SRC/main/` — его копия для истории, сравнения и проверок ТЗ-5. После каждого изменения в базе — частичная выгрузка и коммит.

## 4. Что сделать [План: шаг 3, «Что делаем»]

### 4.1. Выгрузить наши объекты основной конфигурации (архитектор, ИИ)

ИИ видел только расширение; наш код в основной конфигурации (`т1кДиадокСервер` и др.) ему нужен, чтобы не дублировать и правильно вызывать.

1. ИИ пишет `SRC/main/objects.txt` — по строке на объект: `CommonModule.т1кДиадокСервер`, `CommonModule.т1кСверкаОказанныхУслуг`, `CommonModule.т1кДиадокДоговора`, `InformationRegister.т1кДиадок_НастройкиДоговоров`, `InformationRegister.т1кЗначенияПроизвольныхПараметров`. Архитектор дополняет, если знает ещё наши объекты для Диадока.
2. Архитектор: `/DumpConfigToFiles SRC\main -listFile SRC\main\objects.txt` (команда — ТЗ-0 §3; частичная выгрузка по списку — S008:L3214-L3240).
3. ИИ: коммит.

Если частичная выгрузка не примет формат списка — выгрузить конфигурацию целиком во временный каталог вне git и скопировать нужные папки (В3-1).

### 4.2. Подключаемый модуль и роль — в основную конфигурацию (поз. 1, 2, 3, 22, 23)

Сейчас ПМ (`ДД_подключаемыйМодуль`) и роль `шхДиадок` — объекты внутри расширения вендора. Прямой загрузки объекта расширения в основную конфигурацию платформа не даёт (S008:L3574-L3600). Используем перепаковку ТЗ-2:

1. `tools/convert.ps1 -Source SRC\ERPDiadok -Out out\prod-cf -UuidMap SRC\postavka\uuid-map.csv -UuidMapReadOnly -Build` — расширение прода целиком становится временным `.cf` (в git не кладём). Карта UUID обязательна: у прода другая сборка вендора (ТЗ-0 v3 Ф18). С картой объекты вендора в этом файле получают те же UUID, что у поставщика в базе, и 1С сопоставит их сама.
2. В тестовой базе: Конфигурация → «Сравнить, объединить с конфигурацией из файла» → `out\prod-cf\...cf` → **без** постановки на поддержку → снять все флажки → отметить только `Обработки.ДД_подключаемыйМодуль` и `Роли.шхДиадок` → «Выполнить». Ключ «включать объекты по неразрешённым ссылкам» **не** ставить: иначе вместе с ролью потянутся объекты вендора.
3. Проверить: обработка и роль появились; права роли ссылаются на объекты поставщика `КонтурДиадок`; `/CheckModules -ThinClient -Server`. Если права роли не сопоставились — роль создаётся заново по списку прав из `SRC/ERPDiadok/Roles/шхДиадок/Ext/Rights.xml` (ИИ готовит список «объект → права», В3-4).
4. В Предприятии: модуль Диадок → Настройки → Расширенные → «Подключаемый модуль» → «Местонахождение» = «Конфигурация», имя `ДД_подключаемыйМодуль` (вендор создаёт ПМ так: `Обработки[Имя].Создать()` — ТЗ-0 v3 Ф2). Настройка хранится в данных; в проде её ставит ТЗ-7.
5. Выгрузить объекты в `SRC/main` (дополнить `objects.txt`), коммит.

Почему так, а не вручную: роль `шхДиадок` содержит права на десятки объектов вендора. Перенос объединением сохраняет их точно, руками — долго и с ошибками [вывод].

### 4.3. Новые общие модули (архитектор создаёт, ИИ пишет код)

| Модуль | Свойства | Назначение |
|---|---|---|
| `т1кДиадокМодули` | Сервер = Да; Вызов сервера = Нет; Привилегированный = Нет | тела перенесённых процедур (поз. 2, 5, 8+13, 9, 14, 16, 24, 26) |
| `т1кДиадокФормы` | Сервер = Да | создание наших элементов на формах вендора (ТЗ-4) |
| `т1кДиадокФормыКлиент` | Клиент (управляемое приложение) = Да | клиентские обработчики наших элементов форм (ТЗ-4) |

Архитектор создаёт пустые модули с этими свойствами и включает их в роль `шхДиадок` (право «Использование» не требуется для общих модулей; включить в подсистему `КонтурДиадок` не нужно — это объект поставщика). Код ИИ кладёт в `SRC/main/CommonModules/<имя>/Ext/Module.bsl`; архитектор переносит в базу копированием текста модуля.

### 4.4. Перенос тел процедур (ИИ)

Для каждой позиции из колонки «Как делаем» = «Тело + зацепка» (реестр):

1. Найти наш блок в `SRC/ERPDiadok` по меткам `ШХ` и описи R1.
2. Перенести тело в процедуру или функцию `т1кДиадокМодули` с понятным именем (имена — ниже).
3. **Правило параметров.** Тело получает всё нужное через параметры, а не через переменные модуля вендора. Если телу нужен объект вендора (ядро, основной модуль), он передаётся параметром.
4. Внутри тела — тот же алгоритм, что сейчас; рефакторинг не делаем (Т-2, Т-30). Исключение — поз. 24: параметр `т1кСоздаватьАвто` передаётся полем структуры `т1кПараметры` (реестр, поз. 24).
5. Вызов из кода вендора на этом шаге **не** делается — его ставит зацепка ТЗ-4. Значит, до ТЗ-4 эталоны по этим позициям не совпадут.

## 6. Критерии приёмки

1. Модули компилируются; smoke S1, S4, S10 — пройдены.
2. Для каждой позиции из списка «Тела» есть процедура в `т1кДиадокМодули`, и у неё есть ссылка в реестре.
3. В `SRC/main` нет кода, который обращается к переменным модулей вендора напрямую (поиск `ОсновнойМодуль.` / `Ядро.` вне параметров — ИИ проверяет и приводит список).
4. Расширение вендора в тестовой базе отсутствует; объекты поставщика не изменены («Настройка поддержки» — все «не редактируется»).

## 7. Чего этот шаг не делает

- Не ставит вызовы из кода вендора — это зацепки ТЗ-4.
- Не трогает формы вендора — ТЗ-4.
- Не меняет алгоритмы доработок.
