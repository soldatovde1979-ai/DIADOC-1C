# ТЗ-1. Два слепка: исходный и целевой эталоны (baseline)

|---|---|
| Пункт плана | Шаг 1 |
| Зависит от | — (первый шаг) |
| Кто делает | ИИ (я) — копирование файлов, симуляция целевого состояния, создание манифестов; человек — ревью целевого слепка |

## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Эталон** | Полная копия выгрузки проекта, снятая для сверки. У нас их будет **две**: исходная и целевая. |
| **Baseline (базлайн)** | То же, что эталон. Английский термин остаётся только в именах папок. |
| **Baseline-Исходный** | Слепок «как есть сейчас», снятый ДО любых правок. Контролирует, что при переносах мы ничего не потеряли. |
| **Baseline-Целевой** | Слепок «как должно быть в конце». Я (ИИ) знаю, куда уйдёт каждый блок (реестр кастомизаций + ТЗ), поэтому сразу создаю копию выгрузки, в которой уже выполнены: нормализация разметки, перенос в хуки, вставки будущих патчей. Это симуляция результата работы скриптов — «фотография цели». |
| **Манифест (`manifest.md5`)** | Текстовый файл: путь к каждому файлу + его MD5. «Список с отпечатками пальцев» — по нему мгновенно видно, изменился ли файл. |
| **MD5** | «Отпечаток пальца» файла: короткая строка, вычисляемая из содержимого. Изменился один символ — MD5 другой. Совпал MD5 → файлы одинаковые байт-в-байт. |
| **`baseline.json`** | Справочник для скриптов: по каждому файлу — MD5 + число ШХ-блоков + позиции реестра, которых касается файл. |
| **ШХ-блок** | Участок кастомизации в коде между `// ШХ ... BEGIN` и `// ШХ ... END`. Сейчас 205 вхождений в 12+ файлах. |
| **Симуляция целевого состояния** | Я вручную (правками файлов в копии, не в рабочей выгрузке) выполняю то, что потом будут делать скрипты: переношу блоки в хук, готовлю вставки. Результат — целевой слепок. |

## 1. Зачем это и что делаем (суть простыми словами)

Автоматизацию переноса доработок нечем проверить: если скрипт потеряет кусок кода — узнаем на боевом экземпляре. Решение — **две фотографии**:

**Фотография 1 — Baseline-Исходный («откуда уходим»).** Копия текущей выгрузки + манифест. Сверка по ней — не целиком (состав кода изменится), а по контролируемым величинам:
- код внутри каждого перенесённого ШХ-блока совпал байт-в-байт;
- число блоков 205 → 205 (в новых местах);
- ни один объект конфигурации не исчез молча.

**Фотография 2 — Baseline-Целевой («куда приходим»).** Так как я знаю, куда уйдёт каждый блок, я сразу **эмулирую конечный результат**: в копии выгрузки выполняю нормализацию разметки, перенос в хуки, вставки патчей — как будто скрипты уже отработали. Дальше скрипты пишутся не «вслепую», а под конкретный, уже существующий образец: **патчер обязан на чистом дистрибутиве выдать байт-в-байт Baseline-Целевой**.

**Правило расхождений:** если выход скриптов ≠ целевому слепку — разбираем и решаем, где ошибка:
- ошибка в скрипте (эталон соответствует замыслу) → чиним скрипт;
- ошибка в эталоне (при симуляции отошли от замысла реестра) → правим эталон.
Решение фиксируется, причина устраняется в источнике.

Ограничение: Baseline-Целевой покрывает **текстовую часть** (модули `.bsl`, реестр патчей). Заимствованные формы и рег. задание создаются в Конфигураторе — их в слепок включить нельзя, они проверяются smoke-тестом (ТЗ-3, ТЗ-7).

## 2. Как использовать

- **Пошаговый контроль (Шаги 2–4).** После каждого шага: блоки на месте, код внутри не изменился — сверка с Исходным; результат шага соответствует целевому — сверка с Целевым.
- **Написание скриптов (Шаги 5–7).** Реестр патчей и патчер составляются так, чтобы их выход = Baseline-Целевой. Тест-скрипт сверяет выход патчера с Целевым слепком по MD5.
- **Расхождения.** По правилу выше: сначала выясняем, где ошибка (скрипт или эталон), потом правим источник.
- **Обновление эталонов.** После изменения кастомизаций или успешного перехода на новую версию вендора оба слепка пересобираются и фиксируются заново.

## 3. Входы / выходы

| | Что | Откуда/куда |
|---|---|---|
| Вход | Текущая выгрузка проекта | `SRC/ERPDiadok/` |
| Выход 1 | Слепок «как есть» | `SRC/Baseline-Исходный/` + `manifest.md5` + `baseline.json` |
| Выход 2 | Слепок «как должно быть» (текстовая часть) | `SRC/Baseline-Целевой/` + `manifest.md5` + `baseline.json` |

## 4. Критерии приёмки

1. Манифесты покрывают 100% файлов каждого слепка.
2. Повторное снятие даёт идентичный результат (фиксированная сортировка).
3. В Исходном число ШХ-блоков = 205; в Целевом — то же число блоков, но в целевых местах (хук, разметка).
4. Каждое изменение в Целевом слепке объяснимо позицией реестра («блок 07-3 переехал в хук ПодготовитьЭлектронныйДокумент») — ничего «самого по себе».

## 5. Что не делает этот шаг

- Не меняет ни один файл рабочей выгрузки — правки только в копиях.
- Не заменяет Шаги 2–4: симуляция в Целевом слепке делается в копии, а рабочие файлы переводятся к целевому состоянию штатными шагами — и сверяются со слепком.

## 6. Связка с реестром кастомизаций

| Позиция реестра | Действие |
|---|---|
| Все 23 позиции | Фиксируются в обоих слепках: в Исходном — как есть, в Целевом — в целевом виде (хук/патч/расширение) |
