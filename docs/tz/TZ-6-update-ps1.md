## 1. Зачем [План: шаг 6, «Зачем»]

Обновление на новый релиз Контура — одной командой на тестовой копии, за час, силами стажёра (my-FT Т-1, Т-5, Т-18). Если скрипт не работает — те же действия руками в Конфигураторе (Т-32).

## 2. Вход [План: шаг 6, «Вход»]

| Что | Где |
|---|---|
| Новый файл модуля | `diadoc_um.cfe` с сайта Контура → положить в `in\` |
| Тестовая база — **свежая** копия прода | разворачивает администратор по регламенту (ТЗ-7) |
| Настройки запуска | `tools/update.config.psd1` (§3.2) |
| Скрипты | `tools/convert.ps1`, `tools/checks/run.ps1`, `tools/lib/v8.ps1` |

## 3. Что сделать [План: шаг 6, «Что делаем»]

### 3.1. Этапы `update.ps1`

Вызов: `tools/update.ps1 -Cfe in\diadoc_um.cfe` (Windows, PowerShell, машина архитектора — ТЗ-0 §3).

| Этап | Что делает | Если ошибка |
|---|---|---|
| 0. Предусловия | git без незакоммиченных изменений; в `$env:DD_IB` не прод (обёртка, ТЗ-0 §4.1); `selftest.ps1` (ТЗ-5 §3.3) зелёный; версия из `.cfe` новее последней метки `vendor-*` | стоп с понятным сообщением |
| 1. Ветка | создать ветку git `update/<версия>` | стоп |
| 2. Перепаковка | `convert.ps1 -Source <cfe> -Out SRC\postavka -UuidMap SRC\postavka\uuid-map.csv -Build` → `dist\Диадок-модуль_<версия>.cf`; коммит «поставка <версия>» | стоп; отчёт `convert.ps1` в журнал |
| 3. Обновление поставщика | `/UpdateCfg dist\Диадок-модуль_<версия>.cf -Settings SRC\postavka\merge-settings.xml -DumpListOfTwiceChangedProperties out\twice.txt` | стоп; лог 1С |
| 4. Обновление базы | `/UpdateDBCfg -Dynamic+` | стоп |
| 5. Наше расширение | `/LoadConfigFromFiles SRC\ext -Extension ДиадокДоработки` → `/UpdateDBCfg -Extension ДиадокДоработки` | стоп |
| 6. Проверки | `tools/checks/run.ps1 -From vendor-<старая>`. Скрипт просит нажать «Сформировать эталоны» и ждёт файлы (ТЗ-5 §3.1) | не стоп: отчёт красный |
| 7. Отчёт | `out\update\<версия>\update.md`: итог, время каждого этапа (секунды), ссылка на отчёт проверок, что делать дальше | — |

Требования:
- `$ErrorActionPreference = 'Stop'`; каждый этап пишет начало, конец и длительность в журнал `out\update\<версия>\log.txt`.
- **Повторный запуск** после исправления продолжает с упавшего этапа: `-From <номер этапа>`. Этапы 2–5 идемпотентны.
- Пароли — только из переменных окружения (ТЗ-0 §3), в файлы не пишутся.
- В прод скрипт **не** ходит. Перенос в прод — по регламенту (ТЗ-7), руками архитектора или стажёра.

### 3.2. Настройки `tools/update.config.psd1`

```powershell
@{
    V8Path      = 'C:\Program Files\1cv8\8.3.27.2130\bin\1cv8.exe'  # платформа
    TestBase    = '<сервер>\<тестовая_база>'                           # где обновляем
    BufferBase  = '<сервер>\<буферная_база>'                           # где собираем поставку
    ProdBase    = '<сервер>\erp_uh'                                    # только чтобы скрипт отказывался с ним работать
    ExtName     = 'ДиадокДоработки'
}
```

Разбор: файл — хеш-таблица PowerShell; читается `Import-PowerShellDataFile`. Пароля в нём нет. В git кладётся `update.config.example.psd1` с плейсхолдерами; рабочий файл — в `.gitignore`.

### 3.3. Конфликты и что с ними делать

Конфликт — красная строка отчёта (ТЗ-5 §3.2). Разбор — по регламенту (ТЗ-7 §4.3): правка зацепки в `SRC/ext` или нашего кода в `SRC/main` → `update.ps1 -From 5`. Позиции 7, 8, 13 и необъяснённые отличия эталонов — архитектору (Т-19).

### 3.4. Снятие эталонов без кнопки (необязательно)

Если на ТЗ-1 найдётся способ получить API вендора во внешней обработке (R6, вариант 2), этап 6 запускает Предприятие с этой обработкой и ждёт результат без человека. Не найдётся — остаётся кнопка; это ~2 минуты и цели (Т-1) не мешает.

## 5. Запасной путь «только Конфигуратор» [План: шаг 6; my-FT Т-32]

Инструкция `docs/zapasnoy-put.md` (одна страница) пишется ИИ по этой таблице. Проверяется в П17 (ТЗ-0) и стажёром.

| Этап скрипта | Руками |
|---|---|
| 2. Перепаковка | Буферная база → Конфигурация → Расширения → Добавить `КонтурДиадок` → «Загрузить из файла» `.cfe` → ПКМ → «Выгрузить конфигурацию в файлы» в пустую папку. В блокноте (Notepad++ — «Найти в файлах / заменить»): (1) удалить строки `<ObjectBelonging>Adopted</ObjectBelonging>` во всех файлах; (2) в `Configuration.xml` удалить строки `ConfigurationExtensionPurpose`, `KeepMappingToExtendedConfigurationObjectsByIDs`, `NamePrefix`; заменить `ConfigurationExtensionCompatibilityMode` на `CompatibilityMode`; удалить два блока `<xr:PropertyState>`; (3) удалить файлы `Ext\SessionModule.bsl` и `Ext\MainSectionCommandInterface.xml`; (4) UUID по карте — для роли `Диадок_БазовыеПрава` заменить UUID на значение из `uuid-map.csv`. Остальные объекты данных не хранят, а наше расширение сопоставляет заимствования по именам (ТЗ-4 §3.1) — их UUID можно не трогать. Удалить расширение из буферной базы → Конфигурация → «Загрузить конфигурацию из файлов» → «Сохранить конфигурацию в файл» `Диадок-модуль_<версия>.cf`. **Если не получается — взять готовый `.cf` прошлого релиза из `dist/` и остаться на нём** |
| 3. Обновление поставщика | Тестовая база → Конфигурация → Поддержка → Обновить конфигурацию → файл `.cf` → «Загрузить настройки» `merge-settings.xml` → Выполнить |
| 4. Обновление базы | Конфигурация → Обновить конфигурацию базы данных |
| 5. Наше расширение | Конфигурация → Расширения → `ДиадокДоработки` → «Загрузить конфигурацию из файлов» `SRC\ext` (если не менялось — пропустить) → Обновить конфигурацию базы данных |
| 6. Проверки | Расширения → `ДиадокДоработки` → «Проверить применимость»; Конфигурация → «Проверка модулей»; кнопка «Сформировать эталоны» и сравнение папок (WinMerge) с `expected\`; smoke |

## 7. Критерии приёмки

1. На тестовой базе (4.61.1 после ТЗ-4) `update.ps1` на релизе 4.70 доходит до отчёта; время этапов 2–5 записано.
2. Повторный запуск `-From 3` после ручной остановки — продолжает без побочных эффектов.
3. На имени прод-базы скрипт отказывается работать.
4. Стажёр проходит запасной путь по инструкции без подсказок (с архитектором рядом), результат равен результату скрипта.

## 8. Чего этот шаг не делает

- Не переносит в прод (ТЗ-7).
- Не чинит конфликты (регламент, ТЗ-7).
