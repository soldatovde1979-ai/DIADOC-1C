# ТЗ-1. Репозиторий: ветка вендора и слияние

| Поле | Значение |
|---|---|
| Версия | 1.0 · 07.10.2026 |
| Шаг плана | 1 |
| Зависит от | TZ-0 (С7 — команды выгрузки, С10/С11 — ретро-данные) |
| Кто делает | ИИ — структура, `.gitattributes`, сборка дерева `main`, скрипт ретро-прогона; человек — свежие выгрузки одной версией платформы |
| Позиции реестра | все (носитель дельты слоёв 2–4) |

## Глоссарий

| Термин | Что это |
|---|---|
| **Ветка `vendor`** | История чистых выгрузок вендора: один коммит на версию. Наш код туда не попадает никогда. |
| **Основная ветка** | Ветка проекта по умолчанию (дальше `main`): дистрибутив вендора + наша дельта + документы. |
| **Слияние (merge)** | `git merge vendor` в `main`. Git сам переносит изменения вендора в наш код. Если вендор и мы меняли одно место, будет **конфликт** с обеими версиями рядом. |
| **Тег** | Именованная метка коммита: `vendor/4.62.0`, `release/4.62.0-1`. |
| **Ретро-прогон** | Пробное слияние уже вышедших версий вендора: сколько конфликтов получилось бы. Калибрует экономику. |

## 1. Что разработать

1. Единый каталог выгрузки расширения: `SRC/КонтурДиадок/`. Вместо пары `SRC/ERPDiadok` + `SRC/TypeDiadok`.
2. Ветка `vendor`: коммит «vendor 4.61.1» = чистый дистрибутив в `SRC/КонтурДиадок/`, тег `vendor/4.61.1`.
3. Основная ветка: слияние `vendor` + коммит «шх: дельта на 4.61.1» = дистрибутив **полностью** (Р-2: без урезания) + наши изменения.
   Удаления объектов (урезание, Ф7) в коммит **не** попадают.
4. `.gitattributes` в корне:
   ```
   SRC/** -text
   ```
   `-text` — git не меняет концы строк и не трогает BOM. Файлы хранятся байт-в-байт, как их выгрузил Конфигуратор.
5. `.gitignore`: `SRC/**/ConfigDumpInfo.xml` — служебный файл, перегенерируется (если С7 подтвердит, что полная загрузка без него работает).
6. Скрипт ретро-прогона `tools/retro.ps1` (§3.4).
7. Правила веток (§2).

## 2. Правила

- В `vendor` коммитятся **только** выгрузки дистрибутива. Сообщение: `vendor <версия>`, тег `vendor/<версия>`.
- Выгрузки `vendor` и основной ветки снимаются **одной версией платформы** (Ф9: иначе шум `<Behavior>` в формах).
  Версия платформы записывается в сообщение коммита.
- Коммит, меняющий вендорский файл в основной ветке, содержит ID точки дельты в сообщении: `шх 07-03: …` (ID — TZ-3).
- История вендора не переписывается. На основной ветке — только слияния, без rebase.
- Каталоги `SRC/ERPDiadok` и `SRC/TypeDiadok` удаляются после того, как п. 3 §1 проверен компиляцией (TZ-4 А1).
  ⚠️ Удаление — после явного «ок» человека.

## 3. Работы

| № | Работа | Кто | Проверка |
|---|---|---|---|
| 3.1 | Человек: свежая выгрузка `TypeDiadok` 4.61.1 (служебная ИБ) и прод-расширения (копия прода) одной версией платформы | человек | Версия платформы одинакова |
| 3.2 | ИИ: orphan-ветка `vendor`, коммит 4.61.1, тег | ИИ | `git ls-tree` = выгрузке |
| 3.3 | ИИ: в основной ветке — `git merge vendor --allow-unrelated-histories`, затем наложение наших изменений поверх полного дистрибутива: изменённые файлы, ПМ, роль, правки `Configuration.xml` (добавление `ДД_подключаемыйМодуль`, `шхДиадок`, режим совместимости — Ф8) | ИИ | `git diff vendor -- SRC` содержит только наши изменения, удалений объектов нет |
| 3.4 | Ретро-прогон (если С11 дал версии новее 4.61.1): для каждой версии — коммит в `vendor`, пробное слияние в одноразовую ветку `retro/<версия>`, отчёт: файлы с конфликтами, число конфликтных участков, участки в файлах с нашей дельтой | ИИ (скрипт), человек (выгрузки) | Отчёт `docs/retro-<дата>.md` |
| 3.5 | Повтор ретро-прогона после Шагов 3–4 — замер, насколько уменьшились конфликты | ИИ | Сравнение двух отчётов |

`tools/retro.ps1` (Windows, PowerShell 5.1+, `$ErrorActionPreference = 'Stop'`): вход — список тегов `vendor/*`;
для каждого — `git switch -c retro/<v> <основная>`, `git merge --no-commit vendor/<v>`, подсчёт `git diff --name-only --diff-filter=U`
и маркеров `<<<<<<<`, `git merge --abort`, удаление ветки. Идемпотентен: ветки `retro/*` пересоздаются.

## 4. Критерии приёмки

1. `git diff vendor/4.61.1 <основная> -- SRC/КонтурДиадок` показывает только нашу дельту: ни одного удалённого объекта вендора.
2. Расширение из основной ветки загружается в тестовую ИБ и проходит проверку модулей (TZ-4 А1).
3. Повторная выгрузка из тестовой ИБ после загрузки не даёт отличий, кроме `ConfigDumpInfo.xml`.
4. Отчёт ретро-прогона (если были версии) приложен.

## 5. Что не делает

- Не меняет логику кода: только раскладка по веткам и восстановление полного дистрибутива.
