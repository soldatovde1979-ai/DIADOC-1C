## 1. Зачем [План: шаг 1, «Зачем»]

Записать, как модуль ведёт себя **сейчас**, пока ничего не тронуто. После каждого следующего шага и при каждом обновлении вендора сравниваем с этой записью программой. Так ошибка переноса видна сразу, а не у пользователей (my-FT Т-4).

## 2. Вход [План: шаг 1, «Вход»]

- Тестовая база — копия прода **в текущем состоянии**, с расширением вендора и нашими правками. Отдельная копия, не та, на которой идут проверки шага 0.
- Тестовый ящик Диадока, если для X6 нужна реальная отправка. Если ящика нет — X6 снимается по загруженному документу.

## 3. Что сделать [План: шаг 1, «Что делаем»]

### 3.1. Служебная команда «Сформировать эталоны» в нашем ПМ (ИИ)

Точка входа вендора найдена по коду ([R6](../research/R6-tochka-vkhoda-etalonov.md)). Используем API, который вендор передаёт в ПМ как `ОсновнойМодуль`: он документирован и меняется реже внутренних функций.

| Требование | Как |
|---|---|
| Где | Наш ПМ `ДД_подключаемыйМодуль`, событие `ЗаполнитьСписокДополнительныхКнопок` — кнопка «Сформировать эталоны» (S010:L91-L93); обработка нажатия — `НажатиеДополнительнойКнопки` |
| Видна только в тестовой базе | условие: константа или параметр запуска `/C ЭТАЛОНЫ`; в проде кнопки нет |
| Ничего не отправляет | только `ЭДО_ПодготовитьПакетКОтправке` и чтение; функции отправки не вызываются |
| Куда пишет | каталог из параметра; для каждого случая папка `X<n>\`: XML документов как отдаёт вендор + `params.json` (ключи по алфавиту) |
| Что пишет | таблица §3.3 |
| Завершение | при запуске с параметром — закрыть сеанс после записи (`ЗавершитьРаботуСистемы(Ложь)`), чтобы скрипт не ждал |

Сейчас ПМ живёт в расширении вендора. Команду добавляем в копию ПМ на тестовой базе. Переезд ПМ в основную конфигурацию — ТЗ-3, команда переезжает вместе с ним.

### 3.2. Случаи (человек готовит документы один раз)

Номера и наименования подготовленных документов записать в колонку «Записано» файла `tools/checks/reference/cases.md` — по ним команда находит документы.

| Случай | Подготовить в тестовой базе | Ожидание (сверить глазами при первом снятии) | Ловит порчу позиций |
|---|---|---|---|
| X1 | Файл входящего УПД (формат 970 или 820), у одной строки `НаимЕдИзм` = «упак», а у товара в справочнике базовая единица «шт». Положить в `tools/checks/reference/input/X1.xml` | У строки единица «упак»; идентификатор номенклатуры содержит единицу (тот же товар в «шт» даёт другой идентификатор) | 7, 25 |
| X2 | Реализация товаров и услуг по договору, где на вкладке Диадок договора включено «Запрашивать подпись контрагента» и задан **отдельный** формат или печатная форма | `ЗапрашиватьОтветнуюПодпись = Истина`; формат и состав печатных форм — как в настройке **договора**; заполнены `т1кПараметры`, `т1кОтправитель`, `т1кПолучатель` | 1, 6, 8, 9, 13, 18 |
| X3 | Та же реализация, тот же контрагент, договор **без** индивидуальной настройки | Всё по общим настройкам контрагента; отличие от X2 — ровно в настроенных полях | 8, 13 |
| X4 | Документ, для которого доступна печатная форма «Сверка» (внешняя ПФ `т1кПечатьСверкиДиадок`), договор услуг | В пакете есть документ по ПФ «Сверка», имя файла по правилу `[ИмяПФ]` | 2 |
| X5 | Реализация с двумя включёнными дополнительными печатными формами | Пакет: основной документ + 2 доп. ПФ; имена файлов и параметры отправки — как в проде | 12 |
| X6 | Включить «Хранить документы в прикреплённых файлах»; загрузить (или отправить в тестовый ящик) один документ | Данные документооборота записаны в прикреплённые файлы и читаются обратно | 10, 14, 20 |
| X7 | Входящий УПД из X1 → «Создать документ поступления» через модуль, как делает автоматизация (режим регламентного создания) | Документ поступления: договор, склад, подразделение из `т1кПараметры`; статья и аналитика расходов; «не списывать на расходы»; номер и дата исправления СФ | 24, 5 |

> **Обратите внимание на X2.** По коду есть подозрение, что формат и печатные формы по договору на этом пути не применяются уже сейчас (R5, «подозрительное место»). При первом снятии сверить глазами именно формат и состав ПФ. Если они не по договору — записать в протокол как **существующее поведение**: переносим его как есть и чиним отдельной задачей (Т-2, Т-30).

| Поле | Откуда | Случаи |

## 5. Критерии приёмки

1. Эталоны X1–X7 сняты; ожидания из §3.2 подтверждены глазами (или расхождение записано как существующее поведение).
2. Повторный прогон на той же базе без изменений даёт «совпало» по всем случаям (маскировка достаточна).
3. Smoke S0–S13 пройден на тестовой базе, результат записан.
4. **Эталоны не слепые.** На копии базы убрать единицу в одном вызове `Новый_НоменклатураЭлектронногоДокумента` → `reference.ps1` показывает отличие в X1. Убрать передачу `Договор1С` в `Документы_ПараметрыОтправкиВидаДокумента` → отличие в X2. Вернуть.

## 6. Чего этот шаг не делает

- Не меняет код вендора и наш код (кроме служебной команды в копии ПМ на тестовой базе).
- Не проверяет новую версию вендора — это ТЗ-5 и ТЗ-8.
