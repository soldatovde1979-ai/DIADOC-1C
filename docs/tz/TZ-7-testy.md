## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Эталон** | Снимок проверенного состояния проекта. Их два (см. ТЗ-1): Baseline-Исходный («как было») и **Baseline-Целевой** («как должно быть» — симуляция результата скриптов). Тест сверяет выход патчера именно с Целевым: совпало байт-в-байт — патчер воспроизводит целевое состояние без человека. |
| **PASS / FAIL** | Итог проверки уровня: PASS — проверка пройдена, FAIL — не пройдена. Протокол — список уровней с их PASS/FAIL. |
| **MD5-сверка** | Сравнение файлов по контрольным суммам, не открывая их (подробно в глоссарии ТЗ-1). Совпали MD5 всех модулей — результат патчера байт-в-байт равен эталону. |
| **Smoke-список** | Перечень ключевых функций, которые обязаны присутствовать в итоговом коде (имя + сигнатура). Тест ищет их текстом и ругается, если хоть одной нет. |
| **Регрессия** | Ситуация «раньше работало, после изменения перестало». Тесты нужны в первую очередь для её ловли. |
| **Проверка чувствительности** | Проверка самого теста: специально портим один ШХ-блок — тест обязан дать FAIL. Если дал PASS — тест слепой, чиним тест. |
| **CI (опционально)** | Continuous Integration — автоматический запуск тестов на сервере при каждом изменении реестра. Необязательный этап, упомянут для полноты. |

## 1. Что разработать
Тест-скрипт `tools/tests/` на OneScript, сценарий пользователя:

```
чистый дистрибутив → прогон патчера → сверка результата с эталоном
```

Уровни проверки:

| Уровень | Что проверяется | Как |
|---|---|---|
| T1. Сборка | Патчер применил все патчи | Отчёт патчера: 0 конфликтов |
| T2. Идентичность | Выход патчера = целевому эталону | MD5 каждого модуля против `SRC/Baseline-Целевой/manifest.md5` |
| T3. Полнота | Все ШХ-блоки на месте | Число блоков и ID = `SRC/Baseline-Целевой/baseline.json` |
| T4. Целостность выгрузки | Парность объектов в `Configuration.xml` | Списки ChildObjects совпадают с эталоном |
| T5. Smoke-список | Ключевые функции присутствуют | Наличие и сигнатуры: `ПодключаемыйМодуль_СовместимыеПараметры`, `НастройкиПечатныхФорм_Прочитать`, `Настройки_ЗначениеСвойства_Диадок`, `Документы_ПараметрыОтправкиВидаДокумента` и др. (список фиксируется из реестра) |

## 2. Как использовать
- Запуск после каждого прогона патчера и после ручного разбора конфликтов.
- CI-режим (опционально): прогон на CI при изменении реестра — защита от регрессии патчей.

## 3. Входы/выходы
- **Вход:** чистый дистрибутив, реестр патчей, эталон.
- **Выход:** протокол `PASS/FAIL` по уровням T1–T5 + diff нерасшедшихся файлов.

## 4. Критерии приёмки
- На эталонной версии вендора все уровни = PASS.
- Тест ловит умышленно внесённую порчу (проверка чувствительности): удаление 1 блока → FAIL на T3.
