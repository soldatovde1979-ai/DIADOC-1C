## 1. Зачем [План: шаг 2, «Зачем»]

Перевести код вендора в слой «поставка»: обычный `.cf`, стоящий в основной конфигурации поставщиком на поддержке. Тогда:
- наше расширение может цепляться за его объекты (ТЗ-4);
- новый релиз ставится одной командой обновления поставщика (ТЗ-6).

## 4. Что сделать [План: шаг 2, «Что делаем»]

### 4.1. Скрипт перепаковки `tools/convert.ps1` (ИИ)

Вызов: `tools/convert.ps1 -Source <путь к .cfe или к каталогу XML> -Out <каталог> [-UuidMap SRC\postavka\uuid-map.csv [-UuidMapReadOnly]] [-Build]`

| № | Что делает | Зачем | Источник |
|---|---|---|---|
| 1 | Если `-Source` — файл `.cfe`: загрузить его в буферную базу как расширение `КонтурДиадок` (`/LoadCfg <cfe> -Extension КонтурДиадок`) и выгрузить в XML (`/DumpConfigToFiles <tmp> -Extension КонтурДиадок`). Если каталог — скопировать | получить XML | S008 |
| 2 | Во **всех** XML удалить строки `<ObjectBelonging>Adopted</ObjectBelonging>` | признак «объект заимствован из основной конфигурации» | S003:L109-L121 |
| 3 | В `Configuration.xml` удалить `ConfigurationExtensionPurpose`, `KeepMappingToExtendedConfigurationObjectsByIDs`, `NamePrefix` | признаки расширения | S075:L51-L56 |
| 4 | Переименовать `ConfigurationExtensionCompatibilityMode` → `CompatibilityMode`, значение не менять | так делает `cfe2cf` (S003:L33); иначе файл не загрузится как конфигурация [вывод, П1] | S003 |
| 5 | **Пустой корень:** удалить блоки `<xr:PropertyState>` (`SessionModule`, `MainSectionCommandInterface`), файлы `Ext/SessionModule.bsl` и `Ext/MainSectionCommandInterface.xml` | корень общий для всех поставщиков — правки в нём конфликтуют (S001:L81). Что они делали, повторяет наше расширение (ТЗ-4 §3.1) | [код] |
| 6 | `<Vendor>` = `СКБ Контур (сборка из расширения)`; `Name` = `КонтурДиадок` и `Version` — как у вендора | имя и поставщик видны в «Настройке поддержки»; слова «сборка из расширения» честно говорят, что это наша сборка, а не поставка Контура | — |
| 7 | **Карта UUID** (если задан `-UuidMap`): для объектов верхнего уровня (роли, обработки, общие модули, подсистема, параметр сеанса, общая команда, картинка, язык) заменить UUID вендора на UUID из карты **во всех файлах** (UUID встречаются в ссылках). Объект, которого нет в карте, — дописать в карту с UUID вендора (с ключом `-UuidMapReadOnly` — не дописывать: так собирается временный файл в ТЗ-3 §4.2). Объект, который есть в карте, но исчез у вендора, — вывести предупреждением | одинаковые UUID между релизами — 1С узнаёт «тот же объект», назначения ролей не слетают | [вывод], П2 |
| 8 | Если загрузка в пустую базу требует свойств конфигурации, которых у расширения нет (язык по умолчанию и т. п.), — добавить их. Список таких свойств фиксируется в скрипте по итогам П1 | — | П1 |
| 9 | С ключом `-Build`: `/LoadConfigFromFiles <Out>` в буферную базу → `/CheckModules -ThinClient -Server` → `/DumpCfg dist\Диадок-модуль_<версия>.cf` | получить файл поставки и убедиться, что модули компилируются | S008 |
| 10 | Отчёт: сколько файлов изменено каждым правилом; новые и исчезнувшие объекты; итог проверки модулей | человек видит, что сделал скрипт | — |

Требования к скрипту:
- `$ErrorActionPreference = 'Stop'`; работает только в своём каталоге `-Out`; исходник не меняет.
- **Идемпотентность:** повторный запуск на тот же вход даёт тот же результат, побайтно.
- Кодировка файлов сохраняется (UTF-8 с BOM).
- Нашей логики в скрипте нет — только правила 1–8 (my-FT Р-3).

### 4.2. Первая сборка и коммит (ИИ + архитектор)

1. Архитектор: `tools/convert.ps1 -Source SRC\TypeDiadok -Out SRC\postavka -Build` (UUID-карта создаётся при первом запуске из UUID 4.61.1).
2. ИИ: проверить отчёт скрипта, закоммитить `SRC/postavka/`, `dist/Диадок-модуль_4.61.1.cf`, `.gitattributes`. Поставить метку `vendor-4.61.1`.

### 4.3. Постановка на поддержку в тестовой базе (архитектор)

Делается на **копии тестовой базы с нашими эталонами** (той, где снимался ТЗ-1). После этого шага база временно без наших доработок — они вернутся в ТЗ-3 и ТЗ-4.

1. Выписать назначения ролей `Диадок_БазовыеПрава` и `шхДиадок` (обработка «Пользователи» → выгрузка списка, или отчёт по профилям групп доступа) → `out\roli-do.txt`.
2. Конфигуратор → Конфигурация → Расширения → `КонтурДиадок` → Удалить.
3. `/MergeCfg dist\Диадок-модуль_4.61.1.cf -Settings SRC\postavka\merge-settings.xml -EnableSupport`.
   - Корень в объединение **не** включается.
   - Все объекты поставщика — правило «Объект поставщика не редактируется»: при обновлении они заменяются целиком (S001:L53-L64), а случайная правка руками невозможна.
4. `/UpdateDBCfg -Dynamic+`.
5. Конфигурация → Поддержка → Настройка поддержки: поставщик `КонтурДиадок` версии 4.61.1 есть, свойства корня ERP не изменились (как в П3).
6. Назначить роль `Диадок_БазовыеПрава` тем же пользователям, что в `out\roli-do.txt`: раньше она давалась всем автоматически как роль расширения по умолчанию (`DefaultRoles`, реестр, таблица 3). Способ — через профиль группы доступа ERP.

## 6. Критерии приёмки

1. Повторный запуск `convert.ps1` на `SRC/TypeDiadok` даёт побайтно те же файлы в `SRC/postavka` (`git status` — без изменений).
2. В тестовой базе в «Настройке поддержки» — поставщик `КонтурДиадок` 4.61.1, все его объекты «не редактируется»; корень ERP без изменений.
3. Модуль Диадок открывается под обычным пользователем (smoke S1, без проверки ПМ — его ещё нет).
4. Расширения вендора в тестовой базе нет.

## 7. Чего этот шаг не делает

- Не возвращает наш код — это ТЗ-3 (основная конфигурация) и ТЗ-4 (расширение). Эталоны на этом шаге **не** совпадут — так и должно быть.
- Не трогает прод (переход — ТЗ-7).
