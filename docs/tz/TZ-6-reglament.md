## 1. Что разработать

`docs/update-checklist.md` и шаблон `docs/update-journal.md`. Разделы регламента:

1. **Когда обновляться.** Ранний прогон `update.ps1 -DryRun` на каждом релизе вендора (≈10 мин). Ставить — по решению,
   но без пропуска нескольких релизов подряд (Р6).
2. **Перед обновлением.**
   - Резервная копия прод-ИБ — **первый обязательный шаг** (Р11).
   - Автообновление модуля выключено и версия модуля в проде = последнему релизу (Р2, по результату С5).
3. **Шаги** — по `update.ps1`, с указанием, что делать при каждом «стоп».
4. **Разбор конфликтов слияния.** По ID точки дельты открыть реестр: «зачем» и «как проверить». Сохранить смысл нашей
   правки на новом коде вендора. Обновить табл. 3, если место сдвинулось. Обязательно просмотреть отчёт Б4
   (новое у вендора в критичных модулях) и нарушения Б3, даже если конфликтов нет.
5. **Загрузка в прод.** Порядок: (1) объекты основной конфигурации, если менялись; (2) расширение `.cfe` из `out/<v>/`;
   (3) обновление БД; (4) smoke-лист. Настройка «Местонахождение ПМ» = «Конфигурация» — проверить.
6. **Откат.** Предыдущий `.cfe` (тег `release/*`, каталог `out/`) загружается обратно. Если обновление изменило структуру
   данных — восстановление из бэкапа шага 2. Когда откат обязателен: ошибка формирования юридически значимых
   документов или отказ модуля при входе.
7. **Новая доработка — иерархия.** (1) событие ПМ → код в `ДД_подключаемыйМодуль`; (2) наш модуль `т1кДиадок*` + одна
   точка вызова с ID; для форм — только программно; (3) встроенная дельта — последнее средство, с ID, строкой
   в табл. 3 и правилом проверки. Коммит содержит ID.
8. **Что проверки не ловят** — перенос plan §8.
9. **Ревизия реестра** на каждом мажорном релизе вендора: мёртвая дельта (Б5), поз. 11, решения TZ-3.
10. **Журнал** — поля: дата, версия вендора, тип релиза (минор / форматы / мажор), время по шагам, конфликты (число, ID),
    причина каждого конфликта (сдвиг / удаление / переписано вендором), время разбора, нарушения проверок, где найдена
    регрессия (проверка / smoke / пользователь), исполнитель.

## 2. Критерии приёмки

1. По регламенту обновление выполняет исполнитель без знания истории проекта. Проверка: прогон «чистым» исполнителем,
   например новым сеансом ИИ без контекста, на ретро-версии или на 4.61.1.
2. Каждый «стоп» `update.ps1` имеет в регламенте действие.
3. Агентские правила (`agent.md`) не противоречат регламенту.
