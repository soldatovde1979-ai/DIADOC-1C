## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Приёмка** | Итоговая проверка всей системы: делаем реальные обновления и меряем, уложились ли в цель по времени и качеству. |
| **Контрольное обновление** | Обновление, выполняемое как экзамен: строго по регламенту, с замером каждого шага. |
| **Метрика** | Измеримый показатель (время, количество). По метрикам решаем, достигнута ли цель. |
| **Тип релиза** | Насколько вендор изменил модуль: минор (исправления), форматы (новые версии электронных документов), мажор (крупная переделка). От типа зависит ожидаемое время. |
| **Точка дельты** | Одна метка ШХ в коде вендора (см. ТЗ-4). Единица счёта конфликтов и автоматического переноса. |
| **«Чистый» исполнитель** | Тот, кто не знает истории проекта: другой человек или новый сеанс ИИ. Проверяет, что регламент действительно самодостаточен. |

## 1. Зачем это и что делаем (суть простыми словами)

Одно удачное обновление ничего не доказывает: релиз мог быть «спокойным» и не задеть наши места. Поэтому приёмка — на **2–3 обновлениях**, по возможности разного типа, с замером каждого шага. Если реальных релизов мало — засчитывается ретро-прогон на уже вышедшей версии, где вендор менял критичные модули.

## 2. Что разработать

Не код — процедура:

1. **База для сравнения.** Если до ввода новой схемы выйдет релиз — обновление по старой схеме замеряется по шагам. Иначе база — оценка «8 ч» с пометкой «не замерено».
2. **Контрольные обновления.** 2–3 обновления по регламенту ТЗ-7 с `update.ps1`. В журнале — тип релиза. Хотя бы одно, по возможности, затрагивает `ГенерацияXML` или `Ядро` в местах нашей дельты.
3. **Чистый исполнитель.** Одно из обновлений (или ретро-прогон) — исполнителем без знания истории.

## 3. Метрики приёмки

| Метрика | Цель |
|---|---|
| Время обновления, сумма по шагам | ≤ 1–1,5 ч в спокойный релиз; для «тяжёлого» — фиксируется |
| Точки дельты, перенесённые слиянием без ручной правки | ≥ 90% |
| Конфликтные точки дельты | ≤ 3 |
| Необъяснённые расхождения эталонных XML | 0 |
| Ошибки компиляции после сборки | 0 |
| Ошибки, найденные пользователями после ввода | 0 |

## 4. Как использовать

- Метрики не достигнуты → по журналу видно, на каком шаге теряется время → доработка именно этого шага.
- Достигнуты → процесс переходит в обычную эксплуатацию; журнал ведётся дальше.

## 5. Входы / выходы

| | Что | Откуда / куда |
|---|---|---|
| Вход | Релизы вендора (или ретро-версии), регламент, `update.ps1` | ТЗ-1, ТЗ-6, ТЗ-7 |
| Выход | Журнал с 2–3 строками | `docs/update-journal.md` |
| Выход | Итоговое решение: ввод в эксплуатацию / доработка (что именно) | `docs/my-FT.md` |
| Выход | Обновлённая таблица 3 реестра, эталоны, теги `release/*` | реестр, `tools/checks/`, git |

## 6. Работы

| № | Работа | Кто | Результат |
|---|---|---|---|
| 8.1 | Замер базы (если будет релиз до ввода) | человек | Строка журнала |
| 8.2 | 2–3 контрольных обновления | человек + ИИ | Строки журнала |
| 8.3 | Прогон «чистым» исполнителем | человек / новый сеанс ИИ | Отметка в журнале |
| 8.4 | Итоговое решение | человек | Запись в `my-FT.md`, отметки `[x]` по требованиям |

## 7. Критерии приёмки

1. В журнале 2–3 обновления с временем по шагам и типом релиза.
2. Метрики §3 достигнуты или для каждой недостигнутой есть план доработки.
3. Регламент пройден «чистым» исполнителем.

## 8. Что не делает этот шаг

- Не меняет архитектуру — только проверяет и даёт данные для доработки.
