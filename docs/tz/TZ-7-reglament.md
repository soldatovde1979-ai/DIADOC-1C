## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Регламент** | Пошаговая инструкция «делай раз, два, три» — настолько подробная, что обновление выполнит человек без знания истории проекта. |
| **Чек-лист** | Список действий с отметками «сделано». Короткая версия регламента для повторных обновлений. |
| **Конфликт слияния** | git не смог сам совместить правку вендора и нашу в одном месте и показал обе версии. Разбирает человек. |
| **Бэкап** | Резервная копия рабочей базы перед обновлением. Без неё откат кода не вернёт данные. |
| **Откат** | Возврат к предыдущей рабочей версии: загрузить прошлый `.cfe`, при необходимости — восстановить базу из бэкапа. |
| **Иерархия решений** | Порядок, в котором выбираем место для новой доработки: сначала событие ПМ, потом наш модуль + точка вызова, и только в крайнем случае — правка внутри кода вендора. |
| **Журнал обновлений** | Таблица: каждое обновление — одна строка с замерами. Нужен для метрик и для прогноза следующих обновлений. |

## 1. Зачем это и что делаем (суть простыми словами)

Инструменты (git, проверки, `update.ps1`) сами по себе не гарантируют результат: важен порядок действий и что делать, когда что-то пошло не так. Регламент отвечает на вопросы, которые возникнут у исполнителя:

- когда обновляться и как не пропустить релизы;
- что сделать **до** обновления, чтобы можно было откатиться;
- что делать на каждой остановке `update.ps1`;
- как разобрать конфликт, если не знаешь историю правки;
- как ставить в прод и как откатить;
- куда класть новую доработку, чтобы она пережила следующее обновление.

## 2. Что разработать

`docs/update-checklist.md` (регламент) и `docs/update-journal.md` (шаблон журнала). Разделы регламента:

1. **Когда обновляться.** Ранний прогон `update.ps1 -DryRun` на каждом релизе вендора (≈10 мин). Ставить — по решению, но не пропускать несколько релизов подряд: конфликты накапливаются.
2. **Перед обновлением.**
   - Резервная копия прод-базы — **первый обязательный шаг**.
   - Автообновление модуля вендором выключено, версия модуля в проде = последнему нашему релизу (по результату С5 ТЗ-0).
3. **Шаги обновления** — по `update.ps1`, для каждой остановки — что делать.
4. **Разбор конфликтов.** По ID метки открыть таблицу 3 реестра: зачем правка, как проверить. Сохранить **смысл** нашей правки на новом коде вендора. Если место сдвинулось — обновить строку в таблице 3. **Обязательно** просмотреть отчёт Б4 (новое у вендора в критичных модулях) и нарушения Б3 — даже если конфликтов нет.
5. **Загрузка в прод.** Порядок: (1) наши объекты основной конфигурации, если менялись; (2) расширение `.cfe` из `out/<версия>/`; (3) обновление базы; (4) smoke-лист. Проверить настройку «Местонахождение ПМ» = «Конфигурация».
6. **Откат.** Загрузить предыдущий `.cfe` (тег `release/*`, каталог `out/`). Если обновление изменило структуру данных — восстановить базу из бэкапа. Откат обязателен, если: документы формируются с ошибками или модуль не запускается.
7. **Новая доработка — куда класть.** (1) Есть подходящее событие ПМ → код в `ДД_подключаемыйМодуль`. (2) Нет → наш модуль `т1кДиадок*` + одна точка вызова с меткой; для форм — только программно, `Form.xml` не трогать. (3) Только если иначе нельзя — правка внутри кода вендора: метка, строка в таблице 3 реестра, правило проверки. ID метки — в подписи коммита.
8. **Что проверки не ловят** — перенос раздела из плана (сценарии вне эталонов, изменения сервиса Диадок, права, внешний вид форм).
9. **Ревизия реестра** на каждом мажорном релизе вендора: мёртвая дельта (Б5), смысл поз. 11, решения ТЗ-4.
10. **Журнал** — поля: дата; версия вендора; тип релиза (минор / форматы / мажор); время по шагам; конфликты (число, ID); причина каждого конфликта (сдвиг / удаление / вендор переписал); время разбора; нарушения проверок; где найдена ошибка (проверка / smoke / пользователь); исполнитель.

## 3. Как использовать

- Первое обновление — по полному регламенту, следующие — по чек-листу.
- При любом отклонении от регламента — запись в журнал и, если нужно, правка регламента.

## 6. Критерии приёмки

1. Обновление по регламенту выполняет исполнитель без знания истории. Проверка: прогон «чистым» исполнителем (например, новым сеансом ИИ без контекста) на 4.61.1 или ретро-версии.
2. Для каждой остановки `update.ps1` в регламенте есть действие.
3. Правила для ИИ (`agent.md`) не противоречат регламенту.
