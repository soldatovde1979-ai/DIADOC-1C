## 1. Зачем [План: шаг 7, «Зачем»]

Один раз перевести прод на новую схему и закрепить порядок для всех следующих обновлений — так, чтобы его выполнял стажёр (my-FT Т-5, Т-18), а решения по рискованным позициям оставались за архитектором (Т-19).

## 2. Вход [План: шаг 7, «Вход»]

- Тестовая база, где всё принято: поставка 4.61.1 на поддержке, наш код, расширение `ДиадокДоработки`, эталоны совпадают, smoke пройден.
- `SRC/postavka`, `SRC/main`, `SRC/ext`, `dist/Диадок-модуль_4.61.1.cf` в git.
- Окно работ на проде, согласованное с пользователями (см. §3.2).

## 3. Переход прода — один раз [План: шаг 7, «Что делаем» — «Переход прода»]

### 3.1. Генеральная репетиция (обязательно)

На **свежей** копии прода (не на тестовой базе, где шла работа) пройти чек-лист §3.3 целиком с секундомером. Записать время каждого пункта. Без успешной репетиции на прод не идём.

### 3.2. Окно и люди

- Окно: вечер или выходной, оценка — время репетиции × 1,5. Пользователи Диадока предупреждены.
- Выполняет архитектор, стажёр наблюдает и ведёт отметки.
- Динамическое обновление возможно (план, Д4; П9), но для первого перехода берём окно: удаляется расширение и меняются роли.

### 3.3. Чек-лист перехода

| № | Действие | Кто | Отметка |
|---|---|---|---|
| 1 | Бэкап базы прода средствами СУБД; плюс `/DumpCfg out\prod_до.cf` и сохранить расширение вендора в файл `out\prod_до_КонтурДиадок.cfe` (`/DumpCfg ... -Extension КонтурДиадок`) | архитектор | |

| 4 | Удалить расширение вендора `КонтурДиадок` | архитектор | |

| 7 | Общие модули `т1кДиадокМодули`, `т1кДиадокФормы`, `т1кДиадокФормыКлиент` — создать и вставить текст из `SRC/main` (ТЗ-3 §4.3) | архитектор | |

### 3.4. Откат перехода

Критерий: любой ❌ в п. 9 или 12, который не устраняется за 30 минут.

1. `/LoadCfg out\prod_до.cf` → `/LoadCfg out\prod_до_КонтурДиадок.cfe -Extension КонтурДиадок` → `/UpdateDBCfg`. Данные переход не меняет — достаточно вернуть конфигурацию и расширение.
2. Вернуть назначения ролей по `out\roli-do.txt`.
3. Smoke по старому листу (S0–S12 v1).
4. Если не помогло — восстановление из бэкапа СУБД (п. 1).

## 4. Регламент обновления — каждый следующий релиз [План: шаг 7, «Что делаем» — «Регламент»]

ИИ пишет `docs/reglament.md` — одна страница для стажёра — по разделам ниже.

### 4.1. Когда

Раз в квартал или при выходе релиза с изменением форматов ФНС (my-FT Т-17). Новые релизы — страница «Новое в модуле» Контура.

### 4.2. Порядок

| № | Шаг | Кто | Время (план §6.3) |
|---|---|---|---|
| 0 | Администратор разворачивает свежую копию прода в тестовую базу | администратор | вне часа обновления |
| 1 | Скачать `diadoc_um.cfe` в `in\` | стажёр | 5 мин |
| 2 | `tools/update.ps1 -Cfe in\diadoc_um.cfe` | стажёр | 20–30 мин |
| 3 | Прочитать `update.md` и отчёт проверок. Зелёный → шаг 5. Красный → шаг 4 | стажёр | 5 мин |
| 4 | Разбор конфликтов (§4.3) → `update.ps1 -From 5` | стажёр / архитектор | 0–30 мин |
| 5 | Smoke на тестовой базе | стажёр | 15–20 мин |
| 6 | Архитектор подтверждает перенос в прод (Т-19) | архитектор | 5 мин |
| 7 | Прод: бэкап → `/UpdateCfg dist\Диадок-модуль_<версия>.cf -Settings SRC\postavka\merge-settings.xml` → `/UpdateDBCfg -Dynamic+` → если менялось `SRC/ext` — загрузить расширение → `/CheckCanApplyConfigurationExtensions` | стажёр | 15 мин |
| 8 | Smoke S1–S4 на проде | стажёр | 5 мин |
| 9 | Влить ветку `update/<версия>` в основную, метка `vendor-<версия>`, время этапов — в журнал обновлений `docs/reglament.md`, раздел «Журнал» | стажёр | 5 мин |

### 4.3. Разбор конфликтов

| Строка отчёта | Что делать | Кто |
|---|---|---|
| Проверка 3: метод вендора изменился | открыть разницу; перенести нашу вставку `т1кДД <ID>` в новый текст метода в `SRC/ext` (копия метода = новый текст вендора + наша вставка) | стажёр; поз. 7, 8, 13 — архитектор |
| Проверка 1: зацепка не применилась | то же, что выше; если метода больше нет — найти, куда вендор перенёс логику; записать в реестр | архитектор |
| Проверка 4: отличие эталона | понять: изменилось поведение вендора (новый формат — нормально, обновить эталон с подтверждения архитектора) или сломалась наша доработка (чинить) | архитектор, если причина не очевидна |
| Проверка 6: элемент формы нарисован вручную | перенести создание в `т1кДиадокФормы` | стажёр |
| Проверка 7: правили объект поставщика | выяснить кто; вернуть объект поставщика; правку — в наше расширение | архитектор |
| Ошибка формы «нет элемента …» на smoke | вендор переименовал элемент формы; поправить `т1кДиадокФормы.Дополнить<Форма>` | стажёр |

### 4.4. Откат обновления на проде

`/LoadCfg` сохранённой перед шагом 7 конфигурации → `/UpdateDBCfg`. Или установить `dist/Диадок-модуль_<прошлая версия>.cf` тем же `/UpdateCfg` — вернётся прошлая версия поставщика.

### 4.5. Правила для новых доработок (чтобы схема не размывалась)

1. Объекты поставщика `КонтурДиадок` **не правим никогда** — они «не редактируется».
2. Новая доработка: сначала событие ПМ; нет события — зацепка в `ДиадокДоработки` с одной строкой вызова; логика — в `т1кДиадокМодули`.
3. Формы — только кодом (Т-11).
4. Каждая доработка — строка в реестре (таблица 1 и 2) и эталон или пункт smoke.

## 6. Критерии приёмки

1. Репетиция пройдена, время записано.
2. Переход прода выполнен; smoke и реальные документы — без ошибок; откат не понадобился (или выполнен и причина устранена).
3. Регламент проверен стажёром: он пересказывает порядок и отвечает, кому эскалировать позиции 7, 8, 13.

## 7. Чего этот шаг не делает

- Не обновляет вендора на новую версию — первое обновление по регламенту — это приёмка (ТЗ-8).
