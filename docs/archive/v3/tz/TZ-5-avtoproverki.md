## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Инвариант** | Условие, которое должно выполняться всегда. Пример: «каждая метка ШХ из реестра есть в коде». Нарушился — значит, что-то потерялось при переносе. |
| **Сигнатурный контроль** | Поиск вызовов функций вендора, в которые мы добавили свой параметр, но конкретный вызов этот параметр не передаёт. Так ловится новая функция вендора, «забывшая» наш договор или единицу измерения. |
| **Опорный элемент** | Элемент формы вендора, к которому привязан наш элемент (см. ТЗ-3). Если вендор его убрал — проверка сообщит заранее, до жалоб пользователя. |
| **Мёртвая дельта** | Наша правка, которую вендор сделал сам в новой версии. Кандидат на удаление. |
| **Отчёт проверок** | Файл `out/checks.md`: что проверено, что нарушено, где именно (файл, строка). |
| **Код возврата** | Число, которое скрипт отдаёт по завершении: 0 — всё хорошо, 1 — найдены нарушения, 2 — сломался сам скрипт. Нужно, чтобы `update.ps1` знал, идти дальше или стоп. |
| **Проверка чувствительности** | Проверка самой проверки: нарочно портим копию кода — скрипт обязан найти порчу. Если не нашёл — он «слепой», чиним скрипт. |

## 1. Зачем это и что делаем (суть простыми словами)

Слияние git переносит наши правки, но не гарантирует, что **смысл** не потерялся. Самые опасные ошибки — тихие: всё собралось, всё «зелёное», а документы уходят контрагентам с неверной единицей или без запроса подписи. Например:

- вендор добавил новую функцию разбора УПД — в ней нет нашей единицы измерения (поз. 7);
- вендор добавил новый вызов чтения настроек — он не передаёт наш договор (поз. 8, 13);
- при разборе конфликта человек случайно удалил нашу метку;
- вендор переименовал кнопку на форме, рядом с которой стоит наша.

Эталонные XML (ТЗ-2) ловят часть этого, но только на 6 тестовых документах. Этот шаг добавляет **проверки по всему коду**: быстрые (секунды), без запуска 1С, с точным указанием места.

## 2. Что разработать

Скрипт `tools/checks/invariants.ps1` (Windows, PowerShell 5.1+, `$ErrorActionPreference = 'Stop'`, чтение файлов UTF-8 с BOM).
Вход — рабочее дерево и ветка `vendor`. Выход — `out/checks.md` и код возврата 0 / 1 / 2.

| № | Проверка | Как работает | Что ловит |
|---|---|---|---|
| Б1 | Метки ↔ реестр | Все метки `ШХ <ID>` в `SRC/КонтурДиадок` сверяются с таблицей 3 реестра: нет лишних, нет пропавших, каждая — в своём файле. Слово `ШХ` без ID — нарушение | Потерянную при слиянии правку; правку, «вшитую» без учёта |
| Б2 | Формы | Файлы форм `Form.xml` в основной ветке совпадают с `vendor`. Каждый опорный элемент из таблицы `т1кДиадокФормы` существует в форме вендора | Ручную правку формы; удалённый вендором опорный элемент |
| Б3 | Сигнатурный контроль | Для каждой функции вендора, у которой в основной ветке больше параметров, чем в `vendor`, находятся **все** её вызовы. Вызов, где аргументов меньше, чем позиция нашего параметра, — нарушение «проверить: вызов без нашего параметра» (файл, строка, функция) | Новые вызовы вендора без `ЕдИзм` (поз. 7) и без `Договор1С` (поз. 8, 13) |
| Б4 | Новое у вендора в критичных модулях | Список функций, добавленных или изменённых вендором между прошлой и новой версией в `ГенерацияXML`, `Ядро`, `ХранениеДанных`. Не нарушение — обязательный материал для просмотра человеком | Новые форматы и функции, которые могут требовать нашей правки |
| Б5 | Мёртвая дельта | Наша метка, код внутри которой после слияния совпал с кодом вендора. **Предупреждение, не нарушение** — обновление не останавливает | Правки, которые вендор сделал сам; кандидаты на удаление |

Скрипт самопроверки `tools/checks/selftest.ps1`: во временной копии (а) удаляет одну метку, (б) убирает наш аргумент из одного вызова из Б3, (в) добавляет элемент в один `Form.xml`. Каждая порча обязана дать нарушение. Запускается при каждом изменении скриптов проверок.

**Состояние на 08.10.2026:** `invariants.ps1` и `selftest.ps1` написаны. Прогон на реальном коде (`TypeDiadok` против `ERPDiadok`, ≈12 с): Б3 нашёл 20 функций с добавленными параметрами, 53 вызова, из них 18 без нашего параметра — совпадает с ручным разбором [R2](../research/R2-signatury.md); Б2 — 46 отличающихся форм из 94 (ожидаемо до ТЗ-3); Б1 — все текущие метки без ID (ожидаемо до ТЗ-4). Самопроверка ловит все порчи. Таблица опорных элементов для Б2 передаётся файлом `-AnchorsFile` (`tools/checks/anchors.csv`, создаётся в ТЗ-3).

## 3. Как использовать

- Автоматически — шаг 5 команды `update.ps1` (ТЗ-6), вместе с компиляцией и эталонами ТЗ-2.
- Вручную — после любой правки кода вендора: `powershell -File tools/checks/invariants.ps1`.
- Отчёт Б4 человек просматривает **при каждом обновлении**, даже если нарушений нет (регламент ТЗ-7).

## 6. Критерии приёмки

1. На итоговой дельте 4.61.1: Б1–Б3 — 0 нарушений. Б5 — каждое предупреждение разобрано: метка удалена (вендор сделал то же) или в таблице 3 записано, почему остаётся.
2. `selftest.ps1` ловит все три порчи.
3. На ретро-версиях (если были в ТЗ-1) Б3 и Б4 показывают найденное; результат приложен к отчёту ретро-прогона.
4. Скрипт отличает «нарушения» (код 1) от «сломался сам» (код 2).

## 7. Что не делает этот шаг

- Не проверяет поведение (это эталоны ТЗ-2) и компиляцию (ТЗ-2) — только текст кода.
- Не исправляет найденное — только сообщает, где и что.
