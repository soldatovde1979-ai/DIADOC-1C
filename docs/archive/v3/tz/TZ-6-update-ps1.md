## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Обёртка** | Один скрипт, который по порядку выполняет все шаги обновления, сам замеряет время и останавливается на первой проблеме. Человеку не нужно помнить порядок команд. |
| **Служебная база** | Пустая база УТ11 только для того, чтобы загрузить в неё новый `.cfe` вендора и выгрузить его в файлы. |
| **Тестовая база** | Копия прода для проверок. Прод скрипт **не трогает никогда**. |
| **Сверка прода** | Проверка «в проде стоит ровно то, что мы выпустили в прошлый раз». Если кто-то срочно поправил прод мимо git — скрипт остановится, иначе эта правка тихо пропадёт. |
| **Ранний прогон (`-DryRun`)** | Шаги 1–5 без сборки релиза. Запускается на каждом новом релизе вендора (~10 мин), даже если ставить пока не собираемся: сразу видно, сколько будет конфликтов. |
| **`-From <шаг>`** | Продолжить с указанного шага. Например, после ручного разбора конфликтов — с шага 5. |
| **Файл настроек `update.config.psd1`** | Пути к базам, к `1cv8.exe`, имя расширения, зафиксированная версия платформы. Паролей в нём нет. |
| **Журнал обновлений** | `docs/update-journal.md`: по строке на каждое обновление — время каждого шага, конфликты, итог. Данные для метрик. |

## 1. Зачем это и что делаем (суть простыми словами)

Даже с git и проверками обновление — это десяток действий: выгрузить, закоммитить, слить, проверить, загрузить, собрать… Каждое можно забыть или сделать не в том порядке. И время никто не замеряет — значит, не понятно, достигли ли цели «1 час».

Решение — **одна команда**:

```
update.ps1 -Cfe "D:\Диадок\KonturDiadok_4.62.0.cfe" -Version 4.62.0
```

Она сама проходит все шаги, на каждом проверяет результат, при проблеме останавливается и пишет, что делать. В конце — строка `МОЖНО СТАВИТЬ` или `СТОП: <причина>` и запись в журнал с временем каждого шага.

## 2. Что разработать

Файлы: `tools/update.ps1`, `tools/update.config.psd1` (пример с пустыми путями). Пароль базы — только переменная окружения `DIADOC_IB_PASSWORD`.

Формат запуска: `update.ps1 -Cfe <путь к новому .cfe> -Version <x.y.z> [-DryRun] [-From <шаг>]`

| Шаг | Что делает | Когда останавливается |
|---|---|---|
| 1. Подготовка | Проверяет: в git нет незакоммиченных изменений; версия платформы = записанной в настройках; `1cv8.exe` на месте | Что-то из этого не так |
| 2. Сверка прода | Выгружает расширение из **копии** прода (или из `.cfe`, выгруженного администратором) и сравнивает с последним релизом (`release/*`) | Есть отличия — значит, прод правили мимо git. Сначала оформить эту правку в git |
| 3. Импорт вендора | Новый `.cfe` → служебная база → выгрузка в файлы → снимок в ветку `vendor`, тег `vendor/<версия>`. Если тег уже есть — шаг пропускается | Ошибка выгрузки |
| 4. Слияние | Ветка `update/<версия>` от основной, слияние `vendor/<версия>` | Конфликты: отчёт со списком файлов и ID меток в них, код 1. После ручного разбора — запуск с `-From 5` |
| 5. Проверки | `invariants.ps1` (ТЗ-5), `compile.ps1` и `reference.ps1` (ТЗ-2) | Любое нарушение — отчёт, код 1 |
| 6. Сборка | Выгружает `.cfe` из тестовой базы в `out/<версия>/`, ставит тег `release/<версия>-<n>` | Ошибка сборки |
| 7. Журнал | Строка в `docs/update-journal.md`: время каждого шага, конфликты (число, ID), нарушения. Тип релиза (минор / форматы / мажор) спрашивает у человека | — |

С `-DryRun` выполняются шаги 1–5, ветка `update/<версия>` потом удаляется, тег `vendor/<версия>` остаётся.

## 3. Как использовать

- **Вышел релиз вендора:** `update.ps1 -Cfe … -Version … -DryRun` → смотрим, сколько конфликтов и нарушений. Решаем, когда ставить.
- **Ставим:** `update.ps1 -Cfe … -Version …` → при конфликтах разбираем по регламенту → `-From 5` → `МОЖНО СТАВИТЬ` → загрузка в прод по регламенту (ТЗ-7, руками).

## 4. Требования к скрипту

- `$ErrorActionPreference = 'Stop'`, `Set-StrictMode -Version Latest`.
- Коды возврата: 0 — готово; 1 — стоп по содержанию (конфликт, нарушение проверок, отличие прода); 2 — сбой выполнения.
- Повторный запуск не дублирует снимки и теги; `-From` продолжает с нужного шага.
- Время начала и конца каждого шага — в `out/<версия>/log.txt`.
- Прод не трогается: загрузка в прод — ручной шаг регламента.

## 5. Входы / выходы

| | Что | Откуда / куда |
|---|---|---|
| Вход | Новый `.cfe` вендора, номер версии | человек |
| Вход | Пути к базам и платформе | `tools/update.config.psd1` |
| Выход | Ветки и теги в git | git |
| Выход | `.cfe` для установки | `out/<версия>/` |
| Выход | Лог и строка журнала | `out/<версия>/log.txt`, `docs/update-journal.md` |

## 7. Критерии приёмки

1. Прогон на 4.61.1 даёт `МОЖНО СТАВИТЬ` и 0 конфликтов.
2. Прогон на версии новее (если есть) доходит до шага 4 или 5 и даёт понятный отчёт.
3. Повторный запуск без изменений ничего не дублирует.
4. Искусственное отличие «прода» останавливает скрипт на шаге 2.

## 8. Что не делает этот шаг

- Не загружает ничего в прод и не обновляет прод-базу.
- Не разбирает конфликты — только показывает их.

|---|---|
| Все | Переносятся шагом 4 (слияние), проверяются шагом 5; конфликты показываются по ID меток таблицы 3 |
