## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Основная конфигурация** | Сама УТ11 с нашими объектами `т1к*`. Обновление модуля Диадок её не трогает — всё, что здесь лежит, переживает обновление само. |
| **Общий модуль** | Модуль 1С с процедурами, которые можно вызывать отовсюду. Флажки «Сервер» / «Клиент» определяют, где он работает. |
| **Точка вызова** | 1–3 строки в коде вендора, которые передают управление нашему модулю. Помечаются `// ШХ <ID>`. Всё, что в этих строках, — наше; остальное — вендора. |
| **Программное изменение формы** | Наши поля, кнопки, команды и обработчики создаёт **код** в момент открытия формы, а не художник формы в Конфигураторе. Файл формы вендора (`Form.xml`) остаётся оригинальным. |
| **Реквизит формы** | Переменная формы, где хранятся данные (например, флажок «режим подписания»). Создаётся кодом: `Форма.ИзменитьРеквизиты(...)`. |
| **Элемент формы** | То, что видно на экране: поле, флажок, кнопка, группа. Создаётся кодом: `Форма.Элементы.Добавить(...)`. |
| **Обработчик** | Процедура, которая срабатывает на событие (нажатие, изменение значения). Назначается кодом: `Элемент.УстановитьДействие("ПриИзменении", "ИмяПроцедуры")`. |
| **Переходник (диспетчер)** | Платформа требует, чтобы обработчик элемента формы лежал **в модуле самой формы**. Поэтому в модуле формы — несколько типовых процедур-переходников, которые просто передают вызов в наш общий модуль. |
| **Опорный элемент** | Элемент формы вендора, рядом с которым мы ставим свой (например, группа кнопок). Если вендор его удалит — наш код поставит элемент в запасное место и предупредит. |
| **Позднее связывание** | Наш модуль получает объект вендора параметром и вызывает его методы по имени во время работы. Поэтому нашему коду не нужно «знать» расширение заранее. |

## 1. Зачем это и что делаем (суть простыми словами)

Сейчас около 2700 строк нашего кода лежат **внутри расширения вендора**. При каждом обновлении вендор присылает новое расширение — и всё наше надо переносить заново. Это и есть «полный день».

Идея шага: **вытащить наш код из расширения вендора в основную конфигурацию**, где обновление его не трогает. В расширении вендора оставить только короткие «точки вызова» — по 1–3 строки.

Три вида переноса:

1. **ПМ целиком** (3699 строк). Ядро вендора умеет брать ПМ из основной конфигурации (Ф2). Переносим обработку как есть и меняем одну настройку.
2. **Наши процедуры из модулей вендора** (хранение в прикреплённых файлах, команда формирования документов). Тело процедуры — в наш общий модуль, в коде вендора — строка вызова.
3. **Формы вендора** (≈1950 строк). Тут нельзя «заимствовать» форму (Ф1), поэтому форму **достраиваем кодом**: при открытии формы наш модуль добавляет поля, кнопки и обработчики. Файл формы вендора остаётся оригинальным — при обновлении приходит новая форма, а наш код достраивает её так же.

Итог: при обновлении переносить нужно не 2700 строк, а несколько десятков строк точек вызова. И переносит их git сам (ТЗ-1).

## 2. Что разработать

### 2.1. Объекты основной конфигурации

| Объект | Вид | Что в нём | Позиции |
|---|---|---|---|
| `ДД_подключаемыйМодуль` | Обработка | ПМ — переносится из расширения как есть (Ф11) | 1, 2, 3, 23; приёмная сторона для 9 |
| `т1кДиадокФормы` | Общий модуль, «Сервер» | Создание наших реквизитов, элементов, команд на формах вендора; серверная часть наших процедур форм; таблица опорных элементов | 17–21 |
| `т1кДиадокФормыКлиент` | Общий модуль, «Клиент» | Клиентская часть наших процедур форм (реакция на нажатия, изменения) | 17–21 |
| `т1кДиадокМодули` | Общий модуль, «Сервер» | Наши процедуры из модулей объектов вендора: хранение в прикреплённых файлах, `ВыполнитьФормированиеДокументов`, вставка поз. 9 | 9, 14, 16 |

Тексты объектов хранятся в git: `SRC/ОсновнаяКонфигурация/<Вид>/<Имя>/…` (структура как у выгрузки) + `SRC/ОсновнаяКонфигурация/README.md` — какие флажки выставить у каждого объекта. Как они попадают в базу (загрузка из файлов или создание руками по тексту) — по результату С10 ТЗ-0.

Существующий модуль `т1кДиадокСервер` **не трогаем**: его текста в репозитории нет.

### 2.2. ПМ (позиции 1, 2, 3, 23)

1. Перенести обработку `ДД_подключаемыйМодуль` в основную конфигурацию, имя то же, код без изменений.
2. Из расширения удалить: сам объект, его регистрацию в `Configuration.xml`, права на него в роли `шхДиадок`.
3. В каждой базе один раз: настройка Диадок «Местонахождение подключаемого модуля» = «Конфигурация» (шаг регламента ТЗ-7).

### 2.3. Наши процедуры из модулей вендора (позиции 14, 16)

- Тело нашей процедуры → `т1кДиадокМодули`. Первым параметром передаётся объект вендора (`ЭтотОбъект`) — через него наш код вызывает нужные методы вендора.
- В коде вендора остаётся точка вызова, например (иллюстрация, точные имена — по коду):
  ```bsl
  // ШХ 14-01
  Если т1кДиадокМодули.ХранитьВПрикрепленныхФайлах(ЭтотОбъект) Тогда Возврат т1кДиадокМодули.ЗаписатьДанныеХранилища(ЭтотОбъект, <параметры>); КонецЕсли;
  ```

### 2.4. Формы (позиции 17–21) — программно

**Что появляется в модуле каждой формы вендора, где есть наша логика** — один типовой блок-переходник (≈25 строк, одинаковый для всех форм):

```bsl
// ШХ 17-00 {
&НаКлиенте
Процедура Подключаемый_ШхСобытие(Элемент) // назначается элементам, созданным нашим кодом
	т1кДиадокФормыКлиент.ОбработатьСобытие(ЭтотОбъект, Элемент);
КонецПроцедуры

&НаКлиенте
Процедура Подключаемый_ШхКоманда(Команда)
	т1кДиадокФормыКлиент.ВыполнитьКоманду(ЭтотОбъект, Команда);
КонецПроцедуры

&НаКлиенте
Функция ШхВыполнитьНаСервереКлиент(ИмяДействия, Параметры = Неопределено) Экспорт // вызывает клиентский модуль
	Возврат ШхВыполнитьНаСервере(ИмяДействия, Параметры);
КонецФункции

&НаСервере
Функция ШхВыполнитьНаСервере(ИмяДействия, Параметры)
	Возврат т1кДиадокФормы.ВыполнитьДействие(ЭтотОбъект, ИмяДействия, Параметры);
КонецФункции
// ШХ 17-00 }
```
Как это работает: элемент, созданный нашим кодом, при нажатии вызывает `Подключаемый_ШхСобытие` → тот передаёт в `т1кДиадокФормыКлиент` → если нужен сервер, клиентский модуль зовёт `ШхВыполнитьНаСервереКлиент` → данные формы уходят в `т1кДиадокФормы` и возвращаются.

**Точки вызова в обработчиках формы вендора:**
- В конце `ПриСозданииНаСервере`: `т1кДиадокФормы.ПриСозданииНаСервере(ЭтотОбъект, Отказ, СтандартнаяОбработка); // ШХ 17-01`. Здесь наш модуль добавляет реквизиты, элементы, команды и назначает обработчики.
- Там, где сейчас наша вставка в обработчик вендора (`ПриОткрытии`, `ПередЗаписью…`, `ОбработкаОповещения`, `ПараметрыОбновленияСпискаДокументов`, `УстановитьВидимость…`) — одна строка вызова нашего модуля на том же месте.
- Если события у формы вендора нет (например `ПриПовторномОткрытии` — сейчас прописано прямо в `Form.xml`, Ф10), оно назначается кодом через `УстановитьДействие` (⚠️ подтверждается в С4).

**Наши элементы в файлах форм (Ф10)** — `шхРежимПодписания`, `шхАвторизован`, `шхТекущиеДокументы`, `шхРежимОткрытияERP`, группа `ГруппаКнопокПодписаниеИОтправка`, `НастройкиПодписание`, правки `НастройкиУправляемая` — создаются кодом. Файлы `Form.xml` возвращаются к оригиналу вендора.

**Опорные элементы.** В `т1кДиадокФормы` — таблица «наш элемент → элемент вендора, рядом с которым ставим → запасное место». Нет опорного элемента → ставим в запасное место и пишем в журнал регистрации предупреждение `Диадок.ШХ.ОпорныйЭлементНеНайден`. Форма открывается, работа не ломается. Таблица же используется проверкой ТЗ-5 (Б2).

**Если наша процедура вызывает внутреннюю процедуру формы вендора** — варианты по порядку предпочтения: (а) вызвать её через форму, если она экспортная клиентская; (б) повторить нужную логику у себя; (в) оставить вызов в модуле формы как встроенную дельту с меткой. Выбор записывается в таблицу 3 реестра.

### 2.5. Порядок работ — от простого к сложному, каждый этап отдельно

| Этап | Что | Почему в этом порядке |
|---|---|---|
| 1 | ПМ → основная конфигурация (поз. 1, 2, 3, 23) | Меньше всего риска: код не меняется, меняется место |
| 2 | `т1кДиадокМодули` (поз. 14, 16, 9) | Серверный код без экранов |
| 3 | Форма `НастройкиУправляемая` (поз. 20, 1 вставка) | Обкатка типового переходника на самой маленькой форме |
| 4 | `ФормаПакетаУправляемая` (поз. 21) | Маленькая |
| 5 | `НастройкаПечатныхФормУправляемая` (поз. 19, ≈770 строк) | Средняя |
| 6 | `ФормаУправляемая` (поз. 17, ≈300 строк + элементы в `Form.xml`) | Есть наши элементы в файле формы |
| 7 | `ФормаЭлементаСправочникаУправляемая` (поз. 18, ≈830 строк) | Самая большая — к этому моменту схема обкатана |

После **каждого** этапа: компиляция + эталоны ТЗ-2 + smoke по затронутым позициям. Не совпало — чиним, к следующему этапу не переходим.

## 3. Как использовать

- **Новая доработка формы вендора** после этого шага: только в `т1кДиадокФормы*` + при необходимости одна точка вызова. Файл формы не трогаем.
- **Обновление вендора:** формы приходят новые, наш код достраивает их при открытии; точки вызова переносит git.

## 6. Критерии приёмки

1. Файлы форм вендора (`Form.xml`) в основной ветке совпадают с веткой `vendor`.
2. В изменённых файлах вендора — только переходники `ШХ <поз>-00` и точки вызова с метками.
3. Компиляция расширения и наших объектов основной конфигурации — без ошибок.
4. Эталоны X1–X6 совпадают с эталонами до рефакторинга.
5. Smoke по позициям 1–3, 14, 16–21, 23 пройден.
6. Каждый из 7 этапов закрыт по пунктам 3–5 до перехода к следующему.

## 7. Что не делает этот шаг

- Не меняет поведение — только место кода. Любое расхождение с эталонами — ошибка этого шага.
- Не трогает позиции 4–8, 10–13, 15 (это ТЗ-4).
