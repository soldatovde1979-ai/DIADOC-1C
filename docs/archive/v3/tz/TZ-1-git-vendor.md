## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **git** | Программа учёта версий файлов. Помнит каждое изменение, умеет сравнивать версии и **сливать** изменения двух людей в одном файле. |
| **Ветка** | Отдельная «линия истории» файлов в git. Изменения в одной ветке не мешают другой, пока их не слили. |
| **Ветка `vendor`** | Ветка, где лежат **только чистые версии вендора**: 4.61.1, потом 4.62 и т. д., по одному снимку на версию. Нашего кода в ней нет никогда. |
| **Основная ветка** | Ветка проекта: дистрибутив вендора + наши изменения + документы. Из неё собирается то, что ставится в прод. |
| **Слияние (merge)** | Команда `git merge vendor`: git смотрит, что вендор изменил между старой и новой версией, и переносит эти изменения в нашу ветку. Наши правки при этом сохраняются. |
| **Конфликт** | Ситуация, когда вендор и мы изменили одно и то же место. git не угадывает, а показывает обе версии рядом — человек выбирает. |
| **Тег** | Именованная метка на снимке: `vendor/4.61.1` — «чистая версия 4.61.1», `release/4.61.1-1` — «наша сборка, ушедшая в прод». |
| **`.gitattributes`** | Файл правил для git. Здесь — правило «не трогать концы строк и кодировку файлов выгрузки», иначе на Windows git будет видеть ложные изменения. |
| **BOM** | Служебная метка кодировки в начале файла. Выгрузка 1С — UTF-8 с BOM; потерять её нельзя, иначе 1С не загрузит файл. |
| **Ретро-прогон** | Репетиция: пробное слияние уже вышедших версий вендора, чтобы заранее увидеть, сколько было бы конфликтов. Ничего не меняет. |

## 1. Зачем это и что делаем (суть простыми словами)

Сейчас при обновлении человек вручную ищет, что поменял вендор, и вручную переносит туда наши правки. Это ровно та работа, для которой придуман git: он умеет сравнивать «старая версия вендора → новая версия вендора» и переносить разницу в нашу версию автоматически.

Для этого нужна правильная раскладка:

- **ветка `vendor`** — чистые версии вендора, одна за другой;
- **основная ветка** — та же версия вендора плюс наши изменения.

Когда выходит новая версия, её кладём в `vendor` и делаем слияние в основную ветку. Всё, что вендор поменял **не там, где наши правки**, переносится само. Там, где пересеклись, — git показывает конфликт с обеими версиями рядом.

Это заменяет из плана v1 сразу три вещи: «нормализацию 205 блоков», «JSON-реестр патчей» и «скрипт-патчер». git умеет больше, чем умел бы наш патчер: переносит новые и удалённые файлы, метаданные (`*.xml`), показывает контекст.

## 2. Что разработать

1. **Единый каталог выгрузки** расширения: `SRC/КонтурДиадок/` — вместо пары `SRC/ERPDiadok` + `SRC/TypeDiadok`.
2. **Ветку `vendor`**: первый снимок — чистый дистрибутив 4.61.1 в `SRC/КонтурДиадок/`, тег `vendor/4.61.1`.
   ⚠️ **Из той же сборки вендора, что стоит в проде** (ТЗ-0 Ф18, С13): UUID расширения и всех объектов прода отличаются от `SRC/TypeDiadok`. Снимок из другой сборки даст конфликты на UUID во всех XML при каждом слиянии.
   Сборку прода не нашли → запасной вариант: снимок `vendor/4.61.1` = выгрузка прода, из которой **откачены** наши правки по описи R1 (код — построчно, метаданные — по таблице 2 реестра). Дороже и требует сверки, поэтому только если С13 не дала результата.
3. **Основную ветку**: слияние `vendor` + наш снимок «шх: дельта на 4.61.1». В нём — дистрибутив **полностью** (без урезания, решение my-FT Р-2) плюс наши изменения: изменённые файлы вендора, ПМ, роль, правки `Configuration.xml` (регистрация `ДД_подключаемыйМодуль`, `шхДиадок`, режим совместимости).
   Удаления объектов вендора (урезание, Ф7) в снимок **не** попадают.
4. **`.gitattributes`** в корне:
   ```
   SRC/** -text
   ```
   Смысл: файлы в `SRC/` git хранит байт-в-байт, не меняет концы строк и не трогает BOM.
5. **`.gitignore`**: `SRC/**/ConfigDumpInfo.xml` — служебный файл Конфигуратора, пересоздаётся сам (если С7 подтвердит, что без него загрузка работает).
6. **Скрипт ретро-прогона** `tools/retro.ps1` (Windows, PowerShell 5.1+):
   - вход — список тегов `vendor/*` (версии новее 4.61.1);
   - для каждой версии: во временной копии рабочей папки (`git worktree`, без новых веток) сделать пробное слияние в основную ветку, посчитать конфликтующие файлы и места, отменить слияние, удалить копию;
   - выход — отчёт `docs/retro-<дата>.md`: версия → файлы с конфликтами → число конфликтных мест → из них в файлах с нашими правками;
   - повторный запуск ничего не портит: основная ветка и рабочая папка не меняются.
   - **Готово:** [tools/retro.ps1](../../tools/retro.ps1), проверен 08.10.2026 на тестовом репозитории с фиктивным Конфигуратором.
7. **Правила работы с ветками** (§3).

## 3. Как использовать (правила)

- В `vendor` кладутся **только** выгрузки дистрибутива. Подпись снимка: `vendor <версия>`, тег `vendor/<версия>`.
- Выгрузки для `vendor` и для основной ветки делаются **одной и той же версией платформы** (Ф9: иначе появляется «шум» в формах). Версия платформы пишется в подпись снимка.
- Любое изменение файла вендора в основной ветке подписывается ID метки ШХ: `шх 07-03: …` (ID — ТЗ-4).
- Историю не переписываем: на основной ветке только слияния, без «перебазирования».
- Каталоги `SRC/ERPDiadok` и `SRC/TypeDiadok` удаляются после того, как основная ветка проверена компиляцией (ТЗ-2). ⚠️ Удаление — только после явного «ок» человека.

## 6. Критерии приёмки

1. Сравнение основной ветки с `vendor/4.61.1` по `SRC/КонтурДиадок` показывает только нашу дельту — ни одного удалённого объекта вендора.
2. Расширение из основной ветки загружается в тестовую базу и проходит проверку модулей (ТЗ-2).
3. Повторная выгрузка из тестовой базы после загрузки не даёт отличий (кроме `ConfigDumpInfo.xml`).
4. Отчёт ретро-прогона приложен (если были версии новее 4.61.1).

## 7. Что не делает этот шаг

- Не меняет логику кода: только раскладывает существующее по веткам и возвращает полный дистрибутив.
- Не трогает прод.
