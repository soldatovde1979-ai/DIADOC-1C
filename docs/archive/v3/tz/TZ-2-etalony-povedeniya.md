## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Эталон поведения** | Записанный результат работы модуля на конкретном тестовом документе: что модуль сформировал и с какими параметрами. «Фотография правильного поведения», с которой потом сравниваем. |
| **Эталонный XML** | Файл электронного документа (УПД, акт и т. п.), который модуль Диадок формирует из документа 1С. Формируем **без отправки** в Диадок. |
| **Параметры пакета** | То, что модуль решает про отправку: запрашивать ли подпись контрагента, какие печатные формы приложить, как назвать файл. Сохраняем рядом с XML в файл JSON. |
| **Тестовый случай (X1–X6)** | Один документ 1С с определёнными условиями (например «реализация по договору с индивидуальной настройкой подписания»), на котором проверяется конкретная доработка. |
| **Маскирование** | Перед сравнением заменяем в файлах то, что меняется при каждом запуске (уникальные идентификаторы, дата формирования, имя файла с датой), на `***`. Иначе файлы всегда «разные». |
| **Проверка модулей (компиляция)** | Конфигуратор проверяет синтаксис всех модулей расширения: нет ли обращений к несуществующим функциям и переменным, правильно ли число параметров. Ловит «вставка встала, но не работает». |
| **Внешняя обработка** | Отдельная обработка 1С в файле `.epf`, которую можно запустить в базе, не меняя конфигурацию. Здесь — инструмент формирования эталонов. |
| **Smoke-лист** | Короткий список ручных проверок на экране (открыть форму, нажать кнопку). Только то, что не проверяется эталонами. |

## 1. Зачем это и что делаем (суть простыми словами)

На Шагах 3–4 мы будем переносить много нашего кода: ПМ — в другое место, процедуры форм — в общие модули, формы — на создание кодом. Код при этом переписывается, а **поведение должно остаться прежним**.

Как доказать, что поведение не изменилось? Снять его «фотографию» **до** правок и сравнивать после каждой правки:

1. **Компиляция** — расширение проходит проверку модулей в тестовой базе. Ловит грубые ошибки: опечатка, не та функция, не то число параметров.
2. **Эталонные XML** — на 6 тестовых документах модуль формирует электронные документы и параметры пакетов. Результат сохраняем. После правок формируем снова и сравниваем: совпало — поведение то же.

Эти же проверки потом каждый раз запускает команда обновления (ТЗ-6): после слияния новой версии вендора результат обязан совпасть с эталонами (или отличаться только там, где вендор сам что-то поменял).

Это **первая в проекте проверка поведения**, а не только текста. В плане v1 её не было (замечания аудита П3, П4).

## 2. Что разработать

### 2.1. Скрипт проверки компиляции `tools/checks/compile.ps1`
- Загружает расширение из `SRC/КонтурДиадок` в тестовую базу и запускает проверку модулей (ключи — по результату С7 ТЗ-0).
- Разбирает лог: ошибок нет → код возврата 0; есть → код 1 и список «модуль : строка : текст ошибки».
- Windows, PowerShell 5.1+, `$ErrorActionPreference = 'Stop'`. Пароль базы — только переменная окружения `DIADOC_IB_PASSWORD`.

### 2.2. Перечень тестовых случаев `tools/checks/reference/cases.md`

| Случай | Документ / данные | Что проверяется | Позиции |
|---|---|---|---|
| X1 | Входящий УПД (сохранённый XML-файл), где у строки `НаимЕдИзм` отличается от справочника | Единица измерения берётся из входящего документа | 7 |
| X2 | Исходящая реализация по договору **с** индивидуальной настройкой подписания | Запрос подписи по договору, параметры т1к, отправитель/получатель | 1, 6, 8, 9, 13, 18 |
| X3 | То же, но договор **без** индивидуальной настройки | Контроль: работают общие настройки | 8, 13 |
| X4 | Сверка оказанных услуг (внешняя печатная форма) | Наша печатная форма «Сверка (ШХ)» | 2 |
| X5 | Пакет с дополнительными печатными формами | Доп. ПФ, имя файла, параметры отправки | 12 |
| X6 | Документ при включённой настройке «хранить в прикреплённых файлах»: запись и чтение | Наше хранилище документов | 10, 14 |

Для каждого случая в файле указано: какой документ подготовить, какие настройки включить, какой результат ожидается словами.

### 2.3. Обработка формирования эталонов `tools/checks/reference/ЭталоныXML`
- Исходники внешней обработки в виде файлов (собирается в `.epf` командой Конфигуратора, ⚠️ ключ уточнить в С7).
- Для каждого случая вызывает ту же цепочку вендора, что кнопка «Подготовить пакет», **но без отправки**.
- Сохраняет в каталог: XML содержимого документа + JSON с параметрами пакета (`ЗапрашиватьОтветнуюПодпись`, имя файла, состав печатных форм, прочитанные настройки по договору). Для X1 — результат разбора (единицы строк). Для X6 — данные, прочитанные обратно из хранилища.
- ⚠️ Точку входа (функцию Ядра, которая формирует документ без отправки) ИИ находит по коду в начале работ. Если готовой функции нет — используется событие ПМ, и это записывается в отчёт.

### 2.4. Скрипт сравнения `tools/checks/reference.ps1`
- Запускает обработку в тестовой базе (режим «Предприятие», ключ `/Execute`).
- Маскирует меняющиеся значения, сравнивает с `tools/checks/reference/expected/`.
- Отчёт по каждому случаю: «совпало» / «отличается: где и что». Код 0 — всё совпало, 1 — есть отличия, 2 — сбой.

### 2.5. Smoke-лист `tools/checks/smoke.md`
По одной строке на позицию реестра — только то, что не покрыто X1–X6: открыть форму, увидеть наш элемент, нажать нашу кнопку, режим пользователя. Цель — пройти за 15–20 минут.

## 3. Как использовать

- **Сейчас (до Шага 3):** человек готовит 6 документов, запускает обработку — получаем эталоны, коммитим в `expected/`.
- **На Шагах 3–4:** после каждой правки — компиляция + сравнение с эталонами + smoke по затронутым позициям. Отличие = ошибка выноса, чиним до следующего этапа.
- **При каждом обновлении вендора:** то же автоматически в `update.ps1` (ТЗ-6). Отличие разбирается: если вендор сам поменял формат — эталон обновляется осознанно, с записью в журнал.

## 6. Критерии приёмки

1. `compile.ps1` на текущей основной ветке: 0 ошибок.
2. Эталоны X1–X6 сняты и закоммичены **до начала ТЗ-3**.
3. Повторный прогон на том же коде даёт «всё совпало» (маскирование работает).
4. Порча: если в тестовой копии убрать одну нашу вставку (например, параметр `ЕдИзм`), сравнение показывает отличие в X1 — проверка не слепая.

## 7. Что не делает этот шаг

- Не меняет код в `SRC/`.
- Не отправляет документы в Диадок.
- Не автоматизирует проверку экранов полностью (Vanessa-ADD — отклонено как дорогое; экраны — в smoke-листе).
