## Исходная постановка (что я хочу)

**Что есть.** Модуль Контур.Диадок для 1С (УТ11), кастомизированный под нас: доработки заполнения документов и выгрузки, размеченные в коде комментарием ШХ (205 блоков в 12+ файлах, 23 позиции по реестру).

**Проблема.** При выходе новой версии вендора обновление занимает **полный рабочий день**: вручную переношу свои доработки в обновлённый код вендора, затем проверяю, что ничего не потерялось и не сломалось.

**Что хочу.** Сократить время обновления на новую версию вендора до **1 часа** (допустимый коридор — до 1–1,5 часа).

**Ограничения и условия:**

1. Доработки никуда не деваются — весь текущий функционал сохраняется.
2. Кастомизации не «вшиваются» в код вендора напрямую, а живут там, где вендор их переживёт обновление.
3. Перенос доработок на новую версию должен быть проверяемым: ошибка переноса ловится автоматически, а не пользователем на боевом экземпляре.
4. Процесс должен воспроизводиться без знания истории проекта — по инструкции.
5. Часть работ выполняет ИИ, часть — человек; распределение зафиксировано в плане.

**Как меряем успех.** Контрольное обновление на очередной версии вендора по секундомеру: суммарное время ≤1–1,5 ч, автоматический перенос ≥90% правок, ручных конфликтов ≤3, регрессия по smoke-списку = 0.
Единицы измерения уточнены в разделе «Как меряем успех» ниже: правка = **точка дельты** (одно наше место в коде вендора).

## Почему план переделан (коротко)

Аудит плана v1 показал, что он не дотягивает до цели по трём причинам. Все три подтверждены чтением кода в `SRC/`.

1. **Нельзя «заимствовать формы в своё расширение».** Модуль вендора — это само по себе расширение 1С (`КонтурДиадок`, тип AddOn).
   Платформа не даёт одному расширению заимствовать объекты другого. Значит, шаг «вынести формы в расширение» из v1 невыполним.
2. **Свой патчер не умел создавать новые объекты** (наш подключаемый модуль, роль, процедуры). На чистом дистрибутиве он не собирал рабочую версию.
3. **Проверки были «сами на себя».** Тест сравнивал результат патчера с эталоном, из которого патчи и делались. Он ловил ошибки патчера, но не ловил ошибки переноса на **новую** версию вендора.

Что меняется: вместо «умно переносить наш код в чужой» — **вынести наш код из чужого**, а остаток переносить стандартным инструментом (git) и проверять поведение, а не только текст.

## Шаг 0. Проверка осуществимости (ТЗ-0)
- Прежде чем вкладываться, на тестовой базе проверяем ключевые допущения плана: ПМ работает из основной конфигурации;
  формы вендора можно достраивать кодом из основной конфигурации; полный дистрибутив вендора встаёт на УТ11;
  автообновление модуля отключается; команды пакетного Конфигуратора работают.
- Результат — таблица «подтвердилось / нет». Если что-то не подтвердилось — план правится до начала Шага 1.

## Шаг 1. Репозиторий: ветка вендора и слияние (ТЗ-1)
- В git заводится ветка `vendor`: в ней лежат только чистые выгрузки вендора, по одной на каждую версию.
- Основная ветка = дистрибутив вендора + наши изменения. Обновление на новую версию = слияние `vendor` в основную ветку.
- Настраивается `.gitattributes` (кодировка и концы строк не портятся).
- Если уже вышли версии новее 4.61.1 — делается **ретро-прогон**: пробное слияние, чтобы заранее увидеть число конфликтов.

## Шаг 2. Эталоны поведения — до любых правок кода (ТЗ-2)
- Настраивается автоматическая проверка компиляции расширения в тестовой базе.
- На текущем (ещё не тронутом) коде по 6 тестовым документам формируются **эталонные XML** и параметры пакетов — без отправки в Диадок.
- Эти эталоны — «фотография правильного поведения». После выноса кода (Шаги 3–4) результат обязан с ними совпасть.

## Шаг 3. Вынос нашего кода из расширения вендора; формы — программно (ТЗ-3)
- ПМ `ДД_подключаемыйМодуль` переезжает в основную конфигурацию целиком (позиции 1, 2, 3, 23).
- Наши процедуры из модулей вендора (позиции 14, 16) переезжают в общий модуль `т1кДиадокМодули`; в вендоре остаётся вызов.
- Формы вендора (позиции 17–21): **наши реквизиты, элементы, команды и обработчики создаются кодом** при открытии формы
  (`т1кДиадокФормы`). Файлы форм вендора (`Form.xml`) возвращаются к оригиналу. В модуле формы остаётся небольшой
  типовой «переходник» и вызовы.
- Порядок — от простого к сложному, по одной форме за раз, с проверкой эталонами после каждой.

## Шаг 4. Встроенная дельта: то, что остаётся в коде вендора (ТЗ-4)
- То, что вынести нельзя (позиции 4–13, 15, 25, 26 и остаток 24: новые параметры функций, вставки в выражения), сокращается до минимума.
- Каждое такое место получает метку `// ШХ <ID>` и строку в таблице 3 реестра.
- По позициям 7 (единицы измерения) и 8+13 (настройки по договорам) — решение человека; варианты по коду уже исследованы ([R5](research/R5-poz7-i-poz8-13.md)).
- По позиции 11 — решение человека: оставить (тогда автообновление выключено навсегда и контролируется) или убрать ([R4](research/R4-avtoobnovlenie-i-poz11.md)).

## Шаг 5. Автоматические проверки (ТЗ-5)
- Скрипт проверяет: все метки ШХ на месте и совпадают с реестром; формы вендора не изменены; в новых вызовах функций
  вендора не потерян наш параметр (единица измерения, договор); что нового появилось у вендора в критичных модулях.
- Сама проверка проверяется: нарочно портим код — проверка обязана упасть.

## Шаг 6. Команда обновления `update.ps1` (ТЗ-6)
- Одна команда выполняет всё обновление по шагам: сверка прода → загрузка новой версии вендора → слияние → проверки → сборка → журнал.
- Останавливается на первой проблеме и пишет, что делать. Замеряет время каждого шага.

## Шаг 7. Регламент обновления (ТЗ-7)
- `docs/update-checklist.md`: пошаговая инструкция, по которой обновление выполнит человек без знания истории проекта.
- Бэкап базы, проверка автообновления, разбор конфликтов, загрузка в прод, откат, правила для новых доработок.

## Шаг 8. Приёмка (ТЗ-8)
- 2–3 реальных обновления по регламенту с секундомером. Фиксация в журнале, сравнение с целью.

### В. Итоговое состояние — как выглядит «после»

1. **Наш код живёт вне вендора**: в основной конфигурации. Обновление вендора его не трогает.
2. **В коде вендора — только короткие метки**: точки вызова и неустранимые вставки, каждая с ID и строкой в реестре.
   Формы вендора не изменены вовсе.
3. **Обновление вендора — конвейер**: загрузили новую версию → `update.ps1` → проверки зелёные → собрали → загрузили.
   Руки человека — только на конфликтах (штатно ≤3 места) и в коротком smoke.

### Окупаемость

- **По времени архитектора:** 12–20 дней проекта ÷ 9,5–11 дней в год ≈ **1–2 года**.
- **Если час стажёра считать равным часу архитектора:** 12–20 ÷ 3,5–7 ≈ 2–6 лет. На деле час стажёра дешевле, поэтому реальная окупаемость ближе к первой цифре.
- **Если В-1 решится в пользу «1 рабочего дня»**, а 3 дня — это календарный срок с ожиданием: архитектор экономит ≈2–4 дня в год, окупаемость — 3–10 лет. Тогда проект оправдывают не часы, а пункты ниже.
- В версии 3.0 плана было «полгода–год» — **ошибка расчёта** (6 обновлений в год и экономия 6 ч вместо фактических данных). Исправлено 08.10.2026.

Выгода, которая в часы не входит:
1. **Передача стажёру.** Сейчас обновление умеет делать только архитектор (bus factor = 1).
2. **Риск тихой потери доработок** — автообновление вендора (Ф17), правки прода мимо git, новые функции вендора без нашей вставки. Сейчас это не ловится ничем.
3. **Проверка поведения** эталонами вместо «посмотрели глазами».

## Как меряем успех

| Метрика | Цель | Откуда берём |
|---|---|---|
| Время обновления, сумма по шагам | ≤ 1–1,5 ч в спокойный релиз | журнал `update.ps1` |
| Время архитектора на обновление | ≤ 5 ч, с 3-го обновления | журнал `update.ps1` (колонка «Исполнитель») + отметка эскалаций |
| Точки дельты, перенесённые слиянием без ручной правки | ≥ 90% | отчёт проверок |
| Конфликты, требующие разработчика | ≤ 3 точки дельты | отчёт слияния |
| Расхождения эталонных XML, не объяснённые изменениями вендора | 0 | отчёт проверок |
| Ошибки компиляции после сборки | 0 | проверка модулей |
| Регрессии, найденные пользователями после ввода | 0 | журнал |

Приёмка — на 2–3 обновлениях: одно спокойное обновление ничего не доказывает.

## Что проверки НЕ ловят (чтобы не было ложного доверия)

- Ошибки в сценариях, которых нет среди эталонов X1–X6 и в smoke-листе.
- Изменения на стороне сервиса Диадок (API, приём форматов).
- Права пользователей, если роли в тестовой базе отличаются от прода.
- Внешний вид программно созданных элементов форм — только глазами в smoke.
