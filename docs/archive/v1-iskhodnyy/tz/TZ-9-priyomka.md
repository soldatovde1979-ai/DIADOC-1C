# ТЗ-9. Приёмка: контрольное обновление

| Поле | Значение |
|---|---|
| Пункт плана | Шаг 9 |
| Зависит от | Все предыдущие ТЗ |
| Кто делает | Человек — контрольное обновление по регламенту; ИИ — помощь в разборе конфликтов и актуализации реестра |
| Статус | Ожидает согласования |

## Глоссарий (термины этого ТЗ)

| Термин | Что это простыми словами |
|---|---|
| **Приёмка** | Итоговая проверка всей системы: делаем реальное обновление на новой версии вендора и замеряем, получилось ли уложиться в цель по времени и качеству. |
| **Метрика** | Измеримый показатель результата (время, доля, количество). Именно по метрикам судим, достигнута ли цель проекта. |
| **APPLIED** | Статус «патч применён автоматически без ручного разбора» (см. ТЗ-6). Доля APPLIED ≥ 90% — целевой показатель. |
| **Контрольное обновление** | Обновление, выполняемое не «в бою», а как экзамен: с секундомером и фиксацией каждого шага. |
| **Актуализированный эталон** | Эталон (ТЗ-1), переснятый после успешного обновления на новую версию вендора. Дальнейшие сверки — уже с ним. |

## 1. Что разработать
Не код — процедура приёмки:

1. Берётся очередная версия вендора (> 4.61.1).
2. Полный прогон по чек-листу ТЗ-8 с секундомером по каждому шагу.
3. Фиксация результатов в журнале обновлений.

## 2. Метрики приёмки
| Метрика | Цель |
|---|---|
| Время обновления суммарно | ≤ 1–1,5 ч |
| Доля автоматически перенесённых правок | ≥ 90% патчей APPLIED без ручного разбора |
| Конфликты, требующие разработчика | ≤ 3 позиций реестра |
| Регрессия функциональности | 0 по smoke-листу |

## 3. Выход приёмки
- Подписанный чек-лист приёмки + актуализированный эталон (ТЗ-1) + обновлённый реестр (версия вендора в `vendorVersion`).
- При успехе процесс передаётся в регламентную эксплуатацию; при отказе — разбор причин и корректировка реестра.

## 4. Реестр
| Позиция реестра | Действие |
|---|---|
| Все 23 | Валидация на новой версии вендора |
