# ТЗ-2. Вынос нашего кода из вендорского расширения; формы — программно

| Поле | Значение |
|---|---|
| Версия | 1.0 · 07.10.2026 |
| Шаг плана | 3 |
| Зависит от | TZ-0 (Г1, Г2, Г4, Г8), TZ-1, TZ-4 часть А (эталоны сняты **до** начала) |
| Кто делает | ИИ — весь код `.bsl`; человек — загрузка в тестовую ИБ, smoke, ревью diff |
| Позиции реестра | 1, 2, 3, 14, 16, 17, 18, 19, 20, 21, 23; точки вызова для 9 |
| Требования | my-FT Т-7, Т-11, Т-12 |

## Глоссарий

| Термин | Что это |
|---|---|
| **Основная конфигурация** | Конфигурация УТ11, в которой уже есть наши объекты `т1к*`. Вендорское обновление её не трогает. |
| **Точка вызова** | 1–3 строки в вендорском модуле, передающие управление нашему модулю. Помечается `// ШХ <ID>`. |
| **Программное изменение формы** | Добавление реквизитов (`ИзменитьРеквизиты`), элементов (`Элементы.Добавить/Вставить`), команд (`Команды.Добавить`) и назначение обработчиков (`УстановитьДействие`) кодом при создании формы. `Form.xml` вендора не меняется. |
| **Диспетчер** | Универсальная процедура в модуле формы (`Подключаемый_Шх…`). Платформа требует, чтобы обработчик динамического элемента был в модуле формы. Диспетчер только перенаправляет вызов в наш модуль. |
| **Опорный элемент** | Элемент вендорской формы, рядом с которым мы вставляем свои (группа, кнопка). Если вендор его удалил, наш код ставит элемент в запасное место и пишет предупреждение. |

## 1. Что разработать

### 1.1. Объекты основной конфигурации

| Объект | Вид | Назначение | Позиции |
|---|---|---|---|
| `ДД_подключаемыйМодуль` | Обработка | ПМ — переносится из расширения как есть (Ф11) | 1, 2, 3, 9 (приёмная сторона), 23 |
| `т1кДиадокФормы` | Общий модуль, Сервер | Программное изменение форм и серверная логика наших процедур форм | 17–21 |
| `т1кДиадокФормыКлиент` | Общий модуль, Клиент | Клиентская логика наших процедур форм | 17–21 |
| `т1кДиадокМодули` | Общий модуль, Сервер | Наши процедуры из вендорских модулей объектов (хранение в прикреплённых файлах, `ВыполнитьФормированиеДокументов`) | 14, 16 |

Тексты хранятся в репозитории: `SRC/ОсновнаяКонфигурация/<Вид>/<Имя>/…` (структура как в выгрузке), плюс `README.md`
с описанием свойств объектов (флаги «Сервер», «Клиент», «Вызов сервера»). Как они попадают в ИБ, решает С10 TZ-0:
загрузка из файлов или создание в Конфигураторе по тексту.

Существующий модуль `т1кДиадокСервер` **не трогаем**: его текста в репозитории нет.

### 1.2. ПМ

1. Перенести `DataProcessors/ДД_подключаемыйМодуль` в основную конфигурацию. Имя то же.
2. Из расширения удалить объект, ссылку в `Configuration.xml` и права в роли `шхДиадок` на этот объект.
3. Настройка Диадок «Местонахождение подключаемого модуля» = «Конфигурация» (однократно в каждой ИБ — шаг регламента).

### 1.3. Процедуры из вендорских модулей объектов (поз. 14, 16)

- Тело нашей процедуры переносится в `т1кДиадокМодули`. Первым параметром передаётся вендорский объект (`ЭтотОбъект`),
  поэтому доступ к его методам остаётся через позднее связывание.
- В вендорском модуле остаётся точка вызова:
  ```bsl
  // ШХ 14-01
  Если т1кДиадокМодули.ХранитьВПрикрепленныхФайлах(ЭтотОбъект) Тогда Возврат т1кДиадокМодули.ЗаписатьДанныеХранилища(ЭтотОбъект, <параметры>); КонецЕсли;
  ```
  (иллюстрация формы точки вызова; точные сигнатуры определяются по коду при выполнении).

### 1.4. Формы (поз. 17–21) — программно

**Шаблон для каждой формы вендора, где есть наша логика** (единый, ≈25 строк, помечен `// ШХ <поз>-00 {` … `}`):

```bsl
// ШХ 17-00 {
&НаКлиенте
Процедура Подключаемый_ШхСобытие(Элемент) // назначается элементам, созданным нашим кодом
	т1кДиадокФормыКлиент.ОбработатьСобытие(ЭтотОбъект, Элемент);
КонецПроцедуры

&НаКлиенте
Процедура Подключаемый_ШхКоманда(Команда)
	т1кДиадокФормыКлиент.ВыполнитьКоманду(ЭтотОбъект, Команда);
КонецПроцедуры

&НаКлиенте
Функция ШхВыполнитьНаСервереКлиент(ИмяДействия, Параметры = Неопределено) Экспорт // вызывает клиентский модуль
	Возврат ШхВыполнитьНаСервере(ИмяДействия, Параметры);
КонецФункции

&НаСервере
Функция ШхВыполнитьНаСервере(ИмяДействия, Параметры)
	Возврат т1кДиадокФормы.ВыполнитьДействие(ЭтотОбъект, ИмяДействия, Параметры);
КонецФункции
// ШХ 17-00 }
```
Серверный вызов передаёт данные формы. Изменённые нашим модулем реквизиты возвращаются на клиент штатно.

**Точки вызова в вендорских обработчиках формы:**
- `ПриСозданииНаСервере` — в конце: `т1кДиадокФормы.ПриСозданииНаСервере(ЭтотОбъект, Отказ, СтандартнаяОбработка); // ШХ 17-01`.
  Здесь наш модуль добавляет реквизиты, элементы, команды и назначает действия.
- Остальные события, где наша логика сейчас вклинивается в вендорский обработчик (`ПриОткрытии`, `ПередЗаписью*`,
  `ОбработкаОповещения`, `ПараметрыОбновленияСпискаДокументов`, `УстановитьВидимость…` и т. п.), — одна строка
  вызова нашего модуля в том месте, где сейчас стоит вставка.
- Событие формы, которого у вендора нет (например `ПриПовторномОткрытии`, сейчас — `OnReopen` в `Form.xml`, Ф10),
  назначается программно `УстановитьДействие` (⚠️ подтвердить в С4) на диспетчер шаблона.

**Статические правки `Form.xml` (Ф10)** — `шхРежимПодписания`, `шхАвторизован`, `шхТекущиеДокументы`, `шхРежимОткрытияERP`,
группа `ГруппаКнопокПодписаниеИОтправка`, `НастройкиПодписание`, правки `НастройкиУправляемая` — переводятся
в программное создание. `Form.xml` возвращаются к дистрибутиву.

**Опорные элементы.** В `т1кДиадокФормы` — таблица «наш элемент → опорный элемент вендора → запасное место».
При отсутствии опорного элемента элемент ставится в запасное место, в журнал регистрации пишется предупреждение
`Диадок.ШХ.ОпорныйЭлементНеНайден`. Таблица — данные для проверки TZ-4 Б2.

**Если наша процедура вызывает локальную процедуру формы вендора**, варианты по убыванию предпочтения:
(а) вызвать её через форму, если она экспортная клиентская; (б) повторить нужную логику в нашем модуле;
(в) оставить вызов в модуле формы как точку дельты слоя 3 с ID. Выбор фиксируется в табл. 3 реестра.

### 1.5. Порядок работ — каждая строка отдельным коммитом с ID и проверкой

| № | Что | Почему в этом порядке |
|---|---|---|
| 1 | ПМ → основная конфигурация (поз. 1, 2, 3, 23) | Меньше всего риска: код не меняется, меняется место |
| 2 | `т1кДиадокМодули` (поз. 14, 16) | Серверный код без UI |
| 3 | Форма `НастройкиУправляемая` (поз. 20, 1 вставка) | Обкатка шаблона на самой маленькой форме |
| 4 | `ФормаПакетаУправляемая` (поз. 21) | Маленькая |
| 5 | `НастройкаПечатныхФормУправляемая` (поз. 19, ≈770 строк) | Средняя |
| 6 | `ФормаУправляемая` (поз. 17, ≈300 строк + `Form.xml`) | Есть статические элементы |
| 7 | `ФормаЭлементаСправочникаУправляемая` (поз. 18, ≈830 строк) | Самая большая, к этому моменту шаблон обкатан |

## 2. Как использовать

- Новая доработка формы вендора: только в `т1кДиадокФормы*` плюс, если нужно, одна точка вызова. `Form.xml` не трогаем.
- Обновление вендора: формы приходят как есть, наш код достраивает их при открытии.

## 3. Входы / выходы

| | Что |
|---|---|
| Вход | Основная ветка после TZ-1; эталоны TZ-4 А |
| Выход | `SRC/ОсновнаяКонфигурация/` с 4 объектами; вендорские файлы — только точки вызова и шаблоны; `Form.xml` = дистрибутив |

## 4. Критерии приёмки

1. `git diff vendor <основная> -- 'SRC/КонтурДиадок/**/Form.xml'` пуст.
2. Каждый изменённый вендорский файл содержит только шаблоны `ШХ <поз>-00` и точки вызова с ID (проверка TZ-4 Б1).
3. Проверка модулей расширения и основной конфигурации без ошибок (TZ-4 А1).
4. Эталонные XML совпадают с эталонами до рефакторинга (TZ-4 А2).
5. Smoke по позициям 1–3, 14, 16–21, 23 (колонка «Как проверить» реестра) пройден.
6. После каждого из 7 этапов §1.5 пункты 3–5 выполнены, до перехода к следующему.

## 5. Что не делает

- Не меняет поведение: только место кода. Любое расхождение эталонов — дефект этого шага.
- Не трогает поз. 4–8, 10–13, 15 (TZ-3).
