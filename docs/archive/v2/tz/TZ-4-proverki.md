## Глоссарий

| Термин | Что это |
|---|---|
| **Проверка модулей** | Синтаксический контроль Конфигуратором всех модулей расширения в тестовой ИБ. Ловит обращения к переименованным переменным и функциям, лишние или недостающие параметры. |
| **Эталонный XML** | Результат формирования электронного документа (и параметров пакета) по фиксированному тестовому документу 1С, сохранённый в файл. После обновления формируется снова и сравнивается. Единственная проверка **поведения**. |
| **Маскирование** | Замена в XML значений, которые меняются от запуска к запуску (GUID, дата формирования, имя файла с датой), на `***` перед сравнением. |
| **Инвариант** | Условие, которое обязано выполняться всегда, например «каждый ID из реестра есть в коде». |
| **Сигнатурный контроль** | Поиск вызовов вендорских функций, которым мы добавили параметр, но вызов этот параметр не передаёт. |
| **Проверка чувствительности** | Нарочно портим код (удаляем ID, аргумент) — проверка обязана упасть. Иначе она слепая. |

## Часть А. До рефакторинга (Шаг 2)

### А1. Компиляция
Скрипт `tools/checks/compile.ps1`: загрузка `SRC/КонтурДиадок` в тестовую ИБ и проверка модулей (`/CheckModules … -Extension`,
ключи — по результату С7). Разбор лога: 0 ошибок → код 0; ошибки → код 1 со списком «модуль: строка: текст».

### А2. Эталонные XML
1. **Тестовые документы** — человек готовит в тестовой ИБ, ИИ даёт перечень (`tools/checks/reference/cases.md`):

| Случай | Документ / данные | Позиции |
|---|---|---|
| X1 | Входящий УПД (сохранённый XML-файл) с `НаимЕдИзм`, отличным от справочника | 7 |
| X2 | Исходящая реализация по договору с индивидуальной настройкой подписания | 1, 8, 9, 13, 18 |
| X3 | То же, договор без индивидуальной настройки (контроль) | 8, 13 |
| X4 | Сверка оказанных услуг (внешняя ПФ) | 2 |
| X5 | Пакет с дополнительными печатными формами | 12 |
| X6 | Документ при включённом «хранить в прикреплённых файлах»: запись и чтение | 14 |

2. **Обработка формирования** `tools/checks/reference/ЭталоныXML` — исходники внешней обработки в XML
   (сборка: `/LoadExternalDataProcessorOrReportFromFiles`, ⚠️ уточнить в С7). Для каждого случая вызывает ту же цепочку
   вендора, что и «Подготовить пакет», **без отправки**. Сохраняет XML содержимого и JSON параметров пакета
   (`ЗапрашиватьОтветнуюПодпись`, имя файла, состав ПФ, прочитанные настройки по договору). Для X1 — структуру разбора
   (единицы строк). Для X6 — прочитанные обратно данные.
   ⚠️ Точку входа (функцию Ядра, формирующую документ без отправки) ИИ определяет по коду в начале работ. Если её нет —
   ищем через ПМ-событие, и это фиксируется в отчёте.
3. Скрипт `tools/checks/reference.ps1`: запуск обработки (`ENTERPRISE /Execute`), маскирование, сравнение с
   `tools/checks/reference/expected/` и отчёт по случаям.
4. Эталоны снимаются на **текущем** коде до начала TZ-2 и коммитятся.

### А3. Smoke-лист
`tools/checks/smoke.md` — по одной строке на позицию из колонки «Как проверить» реестра. Только то, что не покрыто X1–X6
(UI форм, команды, режим пользователя). Цель — не дольше 15–20 минут.

## Часть Б. Инварианты на итоговой дельте (Шаг 5)

Скрипт `tools/checks/invariants.ps1` (PowerShell 5.1+, `$ErrorActionPreference = 'Stop'`, чтение UTF-8 с BOM).
Вход — рабочее дерево и ветка `vendor`. Выход — отчёт `out/checks.md`, код 0 / 1 (нарушения) / 2 (сбой скрипта).

| № | Проверка | Как | Ловит |
|---|---|---|---|
| Б1 | ID ↔ реестр | Все маркеры `ШХ <ID>` в `SRC/КонтурДиадок` ↔ табл. 3 реестра: нет лишних, нет пропавших, каждый ID в своём файле. Маркер `ШХ` без ID — нарушение | Потерянную при слиянии точку, «вшитую» правку без учёта |
| Б2 | Формы | `git diff --quiet vendor -- '**/Form.xml'`; каждый опорный элемент из таблицы `т1кДиадокФормы` есть в `Form.xml` вендора | Статическую правку формы, удалённый вендором опорный элемент |
| Б3 | Сигнатурный контроль | Для каждой функции, чья сигнатура в основной ветке отличается от `vendor`, найти все вызовы в дереве. Вызов с числом аргументов меньше позиции нашего параметра → нарушение «проверить: вызов без нашего параметра» (файл, строка, функция) | Новые функции и вызовы вендора без `ЕдИзм` (поз. 7) и `Договор1С` (поз. 8, 13) — риск Р3 |
| Б4 | Новое у вендора в критичных модулях | Список функций, добавленных или изменённых в `vendor` между прошлым и новым тегом, в `ГенерацияXML`, `Ядро`, `ХранениеДанных` | Материал для обязательного обзора человеком |
| Б5 | Мёртвая дельта | Точка дельты, текст которой после слияния совпал с вендорским (`vendor` сделал то же) | Кандидатов на удаление (Р7) |

### Б6. Чувствительность
`tools/checks/selftest.ps1`: во временной копии удаляет маркер одного ID, аргумент одного вызова из Б3, добавляет
элемент в один `Form.xml`. Каждая порча обязана дать нарушение. Запускается при изменении скриптов проверок.

## Критерии приёмки

1. А1–А2 работают на текущем коде; эталоны X1–X6 зафиксированы до начала TZ-2.
2. Б1–Б5 дают 0 нарушений на итоговой дельте 4.61.1; Б6 ловит все три порчи.
3. На ретро-прогоне (если есть версии) Б3 и Б4 показывают найденное. Результат приложен к отчёту TZ-1 §3.5.
4. Список «что проверки не ловят» (plan §8) перенесён в регламент.
