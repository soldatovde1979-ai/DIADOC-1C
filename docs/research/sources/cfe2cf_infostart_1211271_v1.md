## Часть 1. Текст статьи

Несколько раз за свой опыт работы с расширениями сталкивался с задачей, когда расширение в конкретную конфигурацию встроить без танцев с бубном не получается. Причины могут быть разные, например:

- формы конфигурации разработаны в обычном режиме;
- режим совместимости конфигурации не поддерживает расширения в нужной мере или вовсе;
- есть ограничения по используемой версии платформы.

До этого момента несколько раз приходилось руками переносить все объекты из расширения в основную конфигурацию, т.к. сравнить-объединить с файлом расширения нет возможности на уровне конфигуратора (а если есть — поправьте в комментариях :), гугление результатов не принесло. При этом велик риск потерять типы реквизитов, если переносить объекты не в порядке их создания в расширении.

В поисках инструмента по сравнению и объединению с расширением на форуме прочитал совет: сравнить содержимое файлов самой конфигурации и файлов расширения. Что собственно и сделал при необходимости в очередной раз пройти тернистый путь объединения.

### 1. Выгружаем расширение в файлы

![Шаг 1 — выгрузка расширения в файлы](https://infostart.ru/upload/iblock/cd8/cd8188b11487813eba5f7c58531d1a3e.png)

Аналогично выгрузил пустую конфигурацию для дальнейшего анализа.

Старый добрый Total Commander быстро показал различия между пустой конфигурацией и расширением. При наличии жёсткой 1С-зависимости можно эту операцию выполнить прямо в конфигураторе через «Сравнить файлы...».

> K: пустая конфигурация нужна только чтобы один раз увидеть разницу. Если просто нужен результат — шаг сравнения можно пропустить, список удаляемых строк ниже уже готов.

### 2. Отличия в Configuration.xml

![Шаг 2 — сравнение Configuration.xml](https://infostart.ru/upload/iblock/e53/e53f6e5924d78b6baa0acb8a8f5f67a9.png)

### 3. Удаляем в файле Configuration.xml строки любым текстовым редактором

```xml
<ConfigurationExtensionPurpose>AddOn</ConfigurationExtensionPurpose>
<ObjectBelonging>Adopted</ObjectBelonging>
<KeepMappingToExtendedConfigurationObjectsByIDs>true</KeepMappingToExtendedConfigurationObjectsByIDs>
<NamePrefix>ПР_</NamePrefix>
```

После удаления не забываем сохранить файл.

> K: `ПР_` — префикс расширения автора, у вас он свой. Удаление строки `NamePrefix` не переименовывает объекты: всё, что называлось `ПР_Что-то`, так и останется с префиксом.
> K: сохранять в той же кодировке, что и был (UTF-8 с BOM, как выгружает платформа) — по памяти, сверить на своём файле.

![Шаг 3 — правка Configuration.xml](https://infostart.ru/upload/iblock/62d/62ddc7a4079c765d29b4099c56d79ade.png)

### 4. Загружаем в пустую конфигурацию файлы из папки, где отредактировали Configuration.xml

После (или такими) нехитрыми действиями получаем объекты расширения в основной конфигурации.

> K: строго говоря, на шаге 4 получается отдельный .cf. В основную конфигурацию объекты попадают следующим шагом — «Сравнить, объединить с конфигурацией из файла», которого в статье нет.

### Где способ работает, а где нет

- **Новые объекты расширения — работает.** Автор подтверждает (№12). Добавление и изменение реквизитов у заимствованных объектов обещал описать позже — в статье так и не появилось.
- **Заимствованные формы, доработанные в дизайнере, — ломаются.** Vladimir Litvinenko (№6): при объединении система предлагает загрузить свойство «Сохраняемая форма», а объединение с приоритетом основной конфигурации всё равно замещает форму целиком — элементы основной формы пропадают. Модули и реквизиты объединяются нормально. Его вывод: ещё один довод менять формы в расширениях программно.
- **Добавленные реквизиты к объектам основной конфигурации, изменённые реквизиты** — открытый вопрос (№7), ответа нет.

> K: итого метод надёжен для «самостоятельного» расширения со своими объектами. Если в расширении в основном заимствования и перехваты (`&Перед`, `&После`, `&Вместо`) — переносить их придётся руками: в обычной конфигурации таких аннотаций нет.

### Ошибки и их причины

| Симптом | Причина / решение | Где |
|---|---|---|
| «Загрузка не должна менять принадлежность основного объекта конфигурации» | Осталась строка `<ObjectBelonging>Adopted</ObjectBelonging>` — удалить | №42–43 |
| «Неверный путь к данным: "Номенклатура.DefaultPicture"» при загрузке формы | Загружал на более свежей платформе, чем выгружал. Выгрузка и загрузка — **на одной версии платформы** | №32–35 |
| После сборки .cf «Сравнить, объединить» видит одни и те же объекты основной конфигурации и .cf как разные | Разные UUID объектов. Автор: так бывает с хранилищем — идентификаторы разъезжаются, правка руками или порядок в хранилище | №45–48 |
| Ошибка при обновлении БД / сохранении после загрузки (8.3.16.1063) | Не разобрано, текст ошибки был только на скриншоте | №29 |

> K: по №42–43 — `ObjectBelonging Adopted` бывает не только в Configuration.xml, но и в xml каждого заимствованного объекта (рядом с `ExtendedConfigurationObject`) — по памяти, проверить поиском по выгрузке: `rg -l "Adopted" <каталог>`.
> K: по №45–48 — для заимствованного объекта UUID в расширении свой, а связь с оригиналом идёт через `ExtendedConfigurationObject`. Поэтому для заимствований «сравнить-объединить» по ID в принципе не сойдётся — нужно сопоставлять по именам (в окне сравнения такая опция есть) — по памяти.

### Данные

- №41 (без ответа): что будет с данными регистра, если перенести его из расширения в основную конфигурацию?

> K: по памяти — данные объектов расширения лежат в своих таблицах. Объект, перенесённый в основную конфигурацию, — для платформы новый, со своей таблицей; сами данные не переедут. Перед удалением расширения данные выгрузить и потом загрузить обратно. Сначала проверить на копии базы.

### Готовые инструменты вместо ручной правки

- **cfe2cf на OneScript** — https://github.com/best-tech/cfe2cf (№9, №26). Удобен для автосборки, cprit использует в Jenkins (№15).
  - Недостаток на 2020: не удаляет `KeepMappingToExtendedConfigurationObjectsByIDs` и `NamePrefix` (№10).
  - «Где кнопка скачать?» (№36) — это скрипт, его клонируют/скачивают архивом с GitHub и запускают через OneScript.
  - Не работает с серверными (SQL) базами без файловой — у pavlo упёрлось в лицензию (№45).
- **EDT** (№28): импортировать проект конфигурации и проект расширения и сравнить/объединить там. Особенно удобно, если есть заимствованные и перерисованные управляемые формы. Обычные формы EDT не тянет.
- **ИР — «Инструменты разработчика»** (tormozit, №13, №19, №40): умеет обратную операцию — свою конфигурацию превращает в расширение. Ссылка: https://infostart.ru/1c/tools/15126/
  - Порядок со слов tormozit (2020): платформа 8.3.10.2375+ → в любой базе с подсистемой ИР открыть общую форму «Выпуск варианта Расширение» → указать «Каталог выпуска» → закрыть конфигуратор этой базы → «Выполнить».

### Обратное направление (.cf → .cfe)

- Тот же приём в обратную сторону: строки не удалять, а **добавить** в Configuration.xml (wtlz №3, подтверждено VitalySh №44 в 2024).
- Ссылка автора на тему форума с подробностями (№38): http://forum.infostart.ru/forum24/topic237765/message2413258/#message2413258

### Актуальность

- 2020 — работает; 2021 — «до сих пор работает» (№31); 2024 — у одного пользователя ошибка принадлежности, решается удалением `ObjectBelonging` (№42–43); 2025 — собирается, но упирается в разные UUID при работе с хранилищем (№45–49).

## Часть 3. То же самое без мыши (пакетный режим конфигуратора)

> K: в статье всё делается через меню. Тот же путь из командной строки — по памяти, ключи сверить со справкой своей версии платформы (`1cv8.exe /?` или документация «Запуск 1С:Предприятия из командной строки»).

ОС: Windows, оболочка: Cmd. Выполнять на машине, где установлена платформа той же версии, на которой потом будете загружать.

```bat
rem 1. Выгрузить расширение в файлы
"C:\Program Files\1cv8\8.3.XX.XXXX\bin\1cv8.exe" DESIGNER /F"D:\Bases\Work" /N"Admin" /P"" /DumpConfigToFiles "D:\cfe2cf\src" -Extension "МоёРасширение" /Out "D:\cfe2cf\dump.log"

rem 2. Вручную удалить 4 строки из D:\cfe2cf\src\Configuration.xml (см. шаг 3 статьи)

rem 3. Загрузить файлы в ПУСТУЮ файловую базу и сохранить в .cf
"C:\Program Files\1cv8\8.3.XX.XXXX\bin\1cv8.exe" DESIGNER /F"D:\Bases\Empty" /LoadConfigFromFiles "D:\cfe2cf\src" /DumpCfg "D:\cfe2cf\result.cf" /Out "D:\cfe2cf\load.log"
```

Разбор:
- `DESIGNER` — запуск конфигуратора в пакетном режиме (без окна).
- `/F"путь"` — файловая информационная база (для серверной — `/S"сервер\база"`).
- `/N`, `/P` — пользователь и пароль базы. Пароль лучше не писать в bat-файл, а передавать из переменной окружения.
- `/DumpConfigToFiles "каталог"` — выгрузка конфигурации в XML-файлы.
- `-Extension "Имя"` — выгружать не основную конфигурацию, а указанное расширение.
- `/LoadConfigFromFiles "каталог"` — загрузка конфигурации из XML-файлов в базу.
- `/DumpCfg "файл.cf"` — сохранить конфигурацию базы в .cf.
- `/Out "файл.log"` — куда писать протокол; без него ошибки пакетного режима не увидеть.

⚠ `/LoadConfigFromFiles` **полностью заменяет** конфигурацию базы. Запускать только на пустой/временной базе, не на рабочей.
