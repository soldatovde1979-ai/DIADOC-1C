# R5. Позиция 7 (единица измерения) и позиции 8+13 (настройки по договору): что делает правка на самом деле и как сократить дельту

> Версия: 1.0 · 07.10.2026 · Исследование по коду (без запуска 1С). Входит в ТЗ-4 §2.2 как материал для решения человека.

## Позиция 7 — единица измерения во входящих документах

### Что выяснилось

| Факт | Где |
|---|---|
| Вендор **уже сам** заполняет `ЕдиницаИзмерения` из `НаимЕдИзм` строки входящего документа — в 8 функциях разбора | `КонтурДиадокГенерацияXML`, строки вида `Результат.ЕдиницаИзмерения = ПолучитьЗначениеXDTO(СтрокаXDTO, "НаимЕдИзм")` |
| Наша правка берёт единицу **из другого места** — из `ДопСведТов` (у вендора — из самой строки) — для формата 970 и других | `НоменклатураЭлектронногоДокумента970` и соседние |
| Наша правка добавляет единицу **в вычисляемый идентификатор номенклатуры**: `ФрагментыПредставления.Добавить(НоменклатураЭД.ЕдиницаИзмерения)` в `ПроверитьЗаполнитьИдентификаторНоменклатуры` | `КонтурДиадокГенерацияXML` ~9481 |
| Парная правка на исходящей стороне — позиция 25 (`СтандартУФ_Модуль_ИнтеграцияУниверсальный`): единица добавлена в данные и представление номенклатуры | R1 |

**Смысл для бизнеса (гипотеза, подтвердить у автора):** один и тот же товар в разных единицах (шт / упак) должен сопоставляться с **разной** номенклатурой 1С. Поэтому единица входит в идентификатор. Запись в реестре («наименование единицы в печатных представлениях») это описывает неточно.

### Варианты

| Вариант | Точек дельты | Риск |
|---|---|---|
| (а) Оставить как есть + сигнатурный контроль (ТЗ-5 Б3) | ≈22 | Новые функции разбора вендора — без нашей правки; ловит Б3 |
| (б) Только 2 места: единица в идентификатор (`ПроверитьЗаполнитьИдентификаторНоменклатуры`) + чтение из `ДопСведТов` там, где вендор читает из строки | ≈2–5 | Нужно проверить на эталоне X1, что результат совпадает |
| (в) Событие ПМ `ЗаполнитьТаблицуСопоставленияНоменклатуры` / `ПравилаСопоставленияДокумента` (R3) | 0 в Ядре | Неизвестно, хватит ли параметров события; проверить С9 |

**Рекомендация ИИ:** (б) — опирается на то, что вендор уже делает сам; проверка — эталон X1 до и после.

### Найдено сигнатурным анализом (R2)
Два вызова `Новый_НоменклатураЭлектронногоДокумента` без `ЕдИзм` — `НоменклатураЭлектронногоСчета29` и `НоменклатураЭлектроннойНакладнойРБ01`. **Это не ошибка**: в обеих функциях вендор сам заполняет единицу строкой ниже. Пример того, что Б3 показывает, а решает человек.

## Позиции 8 + 13 — настройки по договору

### Что выяснилось

| Факт | Где |
|---|---|
| Договор берётся **в одном месте**: `Пакеты_ДобавитьДокументВПакет` читает реквизит `Договор` документа 1С | `КонтурДиадокЯдро` ~32280 |
| Дальше он передаётся **новым параметром** через 20 функций (изменены их сигнатуры) | R2 |
| В `ХранениеДанных` уже есть второй способ: договор берётся из структуры `ДанныеКонтрагента.Договор1С` (`Настройки_ЗаполнитьОбщиеПараметрыЗапроса_Диадок`, Красавин) | `КонтурДиадокХранениеДанных` ~594 |
| Структура `ДанныеКонтрагента` **кэшируется на сеанс** (`ХранениеДанных_ДанныеКонтрагента` → `Кэш_Прочитать("ДанныеКонтрагента")`) | `КонтурДиадокЯдро` ~15964 |
| Ключ кэша настроек печатных форм учитывает договор (`НастройкиПечатныхФорм_КлючНастроек`) | `КонтурДиадокЯдро` ~2827 |
| Сами настройки по договору лежат в нашем регистре `т1кДиадок_НастройкиДоговоров` (основная конфигурация), запись — в `Справочники_ЗаписатьЗначениеНастроекКонтрагентов_Диадок` | R1 |

### Варианты

| Вариант | Точек дельты | Риск |
|---|---|---|
| (а) Оставить сквозной параметр + сигнатурный контроль | ≈50 мест в 20 функциях | Каждая новая функция чтения настроек у вендора — без договора; Б3 ловит, но ручной разбор на каждом обновлении |
| (б) «Контекст договора» в переменной модуля | ≈3–5 | Договор может «протечь» на следующий документ пакета, если не сброшен; нужен строгий сброс |
| (г) **Копия** `ДанныеКонтрагента` с полем `Договор1С` в единственной точке входа (`Документы_ПараметрыОтправкиВидаДокумента`), чтение в `ХранениеДанных` уже есть | ≈5–8 | Класть договор в **сам** кэшированный объект нельзя — протечёт. Только копия. Нужно проверить, что ни одна функция по пути не берёт `ДанныеКонтрагента` заново из кэша по идентификаторам |

**Рекомендация ИИ:** исследовать (г) первым — половина механизма уже написана (Красавин), утечки нет при передаче копии. Проверка — эталоны X2 (договор с настройкой) и X3 (без настройки) до и после.

### Подозрительное место для проверки человеком
`Документы_ПараметрыОтправкиВидаДокумента` получает `Договор1С`, но внутри вызывает `НастройкиДокументов_ФорматВидаДокумента` и `НастройкиПечатныхФорм_Прочитать` **без** него (R2, Ядро ~32486–32487). Возможно, формат и печатные формы по договору для этого пути не применяются. Проверить эталоном X2 (смотреть формат и состав ПФ, а не только «запрашивать подпись»).
