## 1. Зачем нужен механизм поддержки

Без него обновление доработанной типовой конфигурации — ручное сличение своей конфигурации с новой версией поставщика и перенос изменений. Механизм поставки/поддержки автоматизирует: платформа сама разносит изменения поставщика по изменённой пользовательской конфигурации и предлагает правила объединения.

## 2. Режимы поддержки

Два режима:

1. **Полная поддержка** (объекты заблокированы, включая запрет добавления новых объектов). Плюс — полностью автоматическое обновление. Два преимущества даже против «ручного» обновления:
   - интегрированная проверка версий — нельзя ошибочно загрузить чужую конфигурацию и потерять данные;
   - обновление компактными файлами `*.cfu`.
2. **Поддержка с возможностью редактирования**. Для перехода: «Конфигурация → Поддержка → Настройка поддержки» → кнопка **«Включить возможность изменения»**. Обратного перевода в полную поддержку **нет**. Снимать конфигурацию с поддержки для редактирования **не требуется** — достаточно включить возможность изменения.

Начальный режим зависит от способа постановки на поддержку:
- установка дистрибутива как новой ИБ или «Загрузить конфигурацию из файла» → полная поддержка;
- объединение пользовательской конфигурации с дистрибутивом поставщика («Сравнить, объединить с конфигурацией из файла…») → поддержка с возможностью редактирования.

## 3. Файлы поставки: cf vs cfu

- Конфигурацию поставщика готовят только командой **«Конфигурация → Поставка конфигурации → Создать поставку»** (создаёт `cf`). Файл, сохранённый через «Сохранить конфигурацию в файл», поставщиком служить **не может**.
- Чтобы передать поставку как `1cd`/`dt`, `cf` загружают (можно в пустую базу) командой «Загрузить конфигурацию из файла», затем выгружают штатно.
- `cf` позволяет обновляться **с любой версии** (в т.ч. откатиться на более старую, чтобы отказаться от своих изменений).
- `cfu` содержит только изменения между конечной версией и перечисленными исходными версиями; обновление возможно **только с указанных версий** — ни с более ранних, ни с более поздних. Пример: конечная версия 4, файл создан для версии 2 — обновление невозможно ни с 1, ни с 3 (защита от «обратных» изменений: если в v3 длину строки увеличили, а в v4 вернули, в cfu это свойство не попадёт, и обновление v3 дало бы неверную длину).
- С точки зрения самого процесса обновление через `cf` и через `cfu` не различается.

## 4. Трёхстороннее сравнение при обновлении

При обновлении изменённой конфигурации участвуют **три** конфигурации:
1. конфигурация пользователя;
2. старая конфигурация поставщика (хранится внутри пользовательской конфигурации);
3. новая конфигурация поставщика.

Правила объединения по умолчанию:

| # | Пользователь | Поставщик | Правило по умолчанию |
|---|---|---|---|
| 1 | менял | не менял | взять из конфигурации пользователя |
| 2 | менял | менял | **требует решения** (жирный шрифт в дереве) |
| 3 | не менял | не менял | взять из конфигурации пользователя |
| 4 | не менял | менял | взять из конфигурации поставщика |

Вариант 2 автоматически разрешить нельзя. Флажок **«Показывать только дважды измененные свойства»** в фильтре просмотра дерева объединения показывает ровно их.

## 5. Правила поддержки объектов (3 шт.)

1. **«Объект поставщика не редактируется»** — при обновлении объект полностью заменяется объектом поставщика новой версии. Устанавливается только для **идентичных** (немодифицированных) объектов и только из диалога сравнения/объединения с конфигурацией поставщика (из окна «Настройка поддержки» платформа его не даст установить). Годится как страховка от случайных изменений.
2. **«Объект поставщика редактируется с сохранением поддержки»** — основное правило; работает трёхстороннее объединение (таблица выше).
3. **«Объект поставщика снят с поддержки»** — объект обновляться не будет. Обязателен перед удалением объекта поставщика.

Расширенная таблица (важные для практической работы строки):

- Пользователь менял / поставщик менял + правило «не редактируется» → **обновление невозможно** (надо снять правило или принять поставщика целиком).
- Пользователь менял / поставщик менял + «снят с поддержки» → взять из пользовательской.
- Пользователь не менял / поставщик менял + «не редактируется» или «с сохранением поддержки» → взять из поставщика.
- Пользователь не менял / поставщик менял + «снят с поддержки» → взять из пользовательской.

**Удаление объекта поставщика**: объект и все его подчинённые должны иметь правило «снят с поддержки». В окне «Настройка поддержки» правило ставится рекурсивно (объект + подчинённые), можно группой объектов.

**Возврат к объекту поставщика** — через диалог сравнения и объединения. Ловушка: если пользователь удалил объект поставщика и затем скопировал его заново из конфигурации поставщика — новый объект логически идентичен, но имеет **другой внутренний идентификатор**; сопоставления с «прежним» объектом в конфигурации БД не произойдёт → возможна потеря данных. Если объект удалили непродуманно, а в конфигурации БД он ещё есть — откатывайтесь к конфигурации БД, а не объединением с поставщиком.

## 6. Прочее из окна «Настройка поддержки»

- Там же: «Снять с поддержки» (вся конфигурация), «Сохранить в файл» (копия конфигурации поставщика), настройка **языков поддержки** (сравнение строк по выбранным языкам — строки на исключённых языках не считаются различающимися), правила по объектам, вызов сравнения/объединения.
- Правило «Объект поставщика не редактируется» ставится только через сравнение/объединение (для идентичных объектов).
- **Хранилище конфигурации**: вся настройка поддержки хранится в **корне конфигурации**; для любых изменений поддержки и для обновления корень должен быть захвачен в хранилище. Для обновления рекомендуется захватывать **всю** конфигурацию.

## 7. Несколько поставщиков

- Любая конфигурация может стоять на поддержке **нескольких** конфигураций поставщиков.
- При обновлении учитываются только объекты, происходящие из конфигурации поставщика; остальные (в т.ч. взятые из другой конфигурации поставщика) считаются «добавленными пользователем» и на обновление не влияют. Для каждого поставщика анализируются только его связи с объектами: обновление из первой конфигурации для второй выглядит как обычное пользовательское редактирование.
- **Сопоставленный объект** (входящий в две поставки): чтобы сохранить поддержку обеих — в обеих настройках поддержки правило «Редактируется с сохранением поддержки». Поддержка одной — в одной «с сохранением», в другой «снят с поддержки». Если у обоих поставщиков «Изменения запрещены» — сопоставить с сохранением обеих поддержек нельзя.
- Минимум один сопоставлённый объект есть всегда — **корень конфигурации**. Критичны его модули приложения и внешнего соединения; их обновление трудоёмко. Рекомендация 1С: выносить существенную функциональность в общие модули, в модулях приложения оставлять только вызовы.
- Постановка на поддержку двух поставщиков: хотя бы для одной поставки — через «Сравнить, объединить с конфигурацией из файла» с предложением встать на поддержку.

## 8. Динамическое обновление и простои (глоссарий + 8.5.4)

- Если изменения не затрагивают структуру данных — обновление **динамическое**, без прерывания работы; активные пользователи подхватывают новую конфигурацию после перезапуска клиента.
- Если структура меняется — основная часть реструктуризации идёт в фоне, но финальная фаза требует **монопольного режима**.
- Перспективно (платформа 8.5.4, анонс): реструктуризация при активных сеансах в клиент-серверном варианте с лицензией КОРП. Сеансы, обратившиеся к обновляемым таблицам, получают исключение «Доступ ограничен. Выполняется обновление конфигурации…», а после завершения — «…Для получения доступа перезапустите приложение» с кнопкой «Перезапустить» в заголовке; незатронутой функциональностью можно продолжать пользоваться. Также обещаны более информативные сообщения об исключительной блокировке (с именем объекта метаданных).

## 9. Расширения: ключевые механики (8.3.15+, из анонса Зазеркалья)

- Аннотации расширения методов: `&Вместо` (полная замена, вся ответственность на расширении), `&Перед`/`&После` (основной сценарий), `&ИзменениеИКонтроль` (компромисс):
  - метод с `&ИзменениеИКонтроль` содержит исходный текст + блоки `#Удалить … #КонецУдалить` (что не выполнять) и `#Вставить … #КонецВставить` (что выполнять вместо);
  - платформа контролирует совпадение исходной части с конфигурацией; при расхождении метод попадает в список ошибок применения расширения, и Конфигуратор предлагает действие **«Восстановить соответствие с методом конфигурации»** (объединение по трём точкам; нужна настроенная внешняя программа сравнения модулей);
  - на один расширяемый метод — только один метод с `&ИзменениеИКонтроль`; второй будет ошибкой применения;
  - метод с этой аннотацией, как и `&Вместо`, полностью заменяет расширяемый метод.
- **Сопоставление заимствованных объектов** — по именам; переименование в конфигурации ломает расширение. С 8.3.15: свойство расширения «Поддерживать соответствие объектам расширяемой конфигурации по внутренним идентификаторам» (по умолчанию Истина) — переименования автоматически отражаются в открытых расширениях; контролируемое свойство «Объект расширяемой конфигурации» хранит внутренний идентификатор. Новые действия при проверке применимости: «Переименовать, сохранив соответствие», «Выбрать соответствие», «Сохранить имя, изменив соответствие», «Установить значение из объекта конфигурации», «Очистить соответствие», «Отключить проверку», «Удалить объект».
- **Основные роли расширений** (8.3.15): автоматическая роль `<Префикс>_ОсновнаяРоль` для собственных объектов; свойство расширения `ИспользоватьОсновныеРолиДляВсехПользователей` (по умолчанию Истина) — все пользователи получают права из основных ролей при подключении; в «Управление расширениями конфигурации» можно управлять ролями (сброс свойства происходит автоматически). В основных ролях — только собственные роли и только права на собственные (не заимствованные) объекты.
