## 1. Конвертация расширения (.cfe) в конфигурацию (.cf) руками — 1211271

Зачем: расширение не всегда можно штатно встроить в конфигурацию (формы в обычном режиме, режим совместимости не поддерживает расширения, ограничение версии платформы), а штатного «сравнить-объединить с файлом расширения» в Конфигураторе нет. Ручной перенос объектов рискует потерять типы реквизитов, если переносить не в порядке их создания.

Порядок:
1. **Выгрузить расширение в файлы** (Конфигуратор, XML-файлы).
2. Выгрузить **пустую конфигурацию** в файлы так же; сравнить структуры (Total Commander; либо прямо в Конфигураторе «Сравнить файлы…»).
3. Отличия — в **`Configuration.xml`**: удалить оттуда 4 строки и сохранить:
   ```xml
   <ConfigurationExtensionPurpose>AddOn</ConfigurationExtensionPurpose>
   <ObjectBelonging>Adopted</ObjectBelonging>
   <KeepMappingToExtendedConfigurationObjectsByIDs>true</KeepMappingToExtendedConfigurationObjectsByIDs>
   <NamePrefix>ПР_</NamePrefix>
   ```
4. **Загрузить в пустую конфигурацию** файлы из папки с отредактированным `Configuration.xml` («Загрузить конфигурацию из файлов»). Получается обычная `.cf`, объекты расширения — в основной конфигурации штатным сравнением/объединением.

Из обсуждения:
- **Официальная альтернатива с 8.3.10.2375+** (tormozit, комм. 19): в окне расширений появился режим «Сделать конфигурацию основной» — платформа сама выполняет такое преобразование (и проверка применимости у него штатная). Стоит попробовать сначала его.
- Готовая автоматизация: **cfe2cf** на oscript — https://github.com/best-tech/cfe2cf (комм. 9, 26).
- Ошибки после конвертации вида `БиблиотекаКартинок.DefaultPicture` (комм. 32–35): в заимствованных формах остаются ссылки на картинки основной конфигурации — ссылки убрать/заменить.
- Если после конвертации при загрузке в конфигуратор ругается на `<ObjectBelonging>Adopted</ObjectBelonging>` в файлах форм (комм. 42–43, 45–48) — эти строки тоже правятся/удаляются (в т.ч. в XML самих форм); при массовых проблемах помогает только аккуратная чистка по файлам.
- Замечание из обсуждения (комм. 6, Владимир Литвиненко): расширение при конвертации даёт «снимок» кода; если расширяемый метод в типовой меняется, обновляться это «cf» не будет — это же относится и к официальному «Сделать конфигурацию основной».
- Обратное преобразование cf→cfe — отдельная задача (комм. 21, 37–38, 40): инструмент «Конфигуратор» не умеет; упомянута обработка «Конструктор конфигурации» (infostart.ru/1c/tools/15126) и ссылка forum24/topic237765.

## 2. Заимствованные формы cfe→cf («четыре строки» + доработки) — 2268137

Задача: перенести в основную конфигурацию заимствованную и доработанную в расширении форму (справочник «Номенклатура»). Инструменты: Конфигуратор + VS Code.

Порядок:
1. Выгрузить конфигурацию расширения в файлы.
2. Открыть структуру в **VS Code**.
3. В `Configuration.xml` удалить те же **4 строки** (см. §1.3) — преобразование типа «расширение» → «конфигурация».
4. Для справочника-владельца формы **разорвать заимствование**: удалить строки со словом `Adopted` у объектов, которые будут импортироваться в основную конфигурацию.
5. «Вырвать» форму из расширения:
   1. удалить `Adopted` у импортируемых объектов;
   2. **сменить идентификатор формы** во всей конфигурации (поиск/замена по файлам — `Ctrl+Shift+H` в vscode): форму оставляют в расширении, а в конфигурацию переносят как новую, чтобы при ошибках переноса сверять с исходником; новый идентификатор — любой уникальный (конкретные цифры не важны);
   3. удалить весь блок `<BaseForm>` в конце файла формы (перед закрывающим тегом) — разрывается связь с расширяемой формой;
   4. у обработчиков событий убрать конструкции вида `callType` (в простейшем случае — удалить эти слова из тега обработчика); имена процедур удобнее переименовать потом в Конфигураторе;
   5. установить номер «1» основного объекта формы: в расширении номера объектов начинаются с миллиона, в основной конфигурации — с единицы.
6. Создать пустую базу → **«Загрузить конфигурацию из файлов»** (модифицированных).
7. Для удобства переименовать форму → выгрузить конфигурацию в **`.cf`**.
8. Типовым сравнением/объединением перенести форму в основную конфигурацию; назначить её формой элемента справочника.
9. Запустить приложение и проверить.

Итог: в основной конфигурации появляется форма, полностью функционально аналогичная доработанной в расширении.

## 3. Восстановление конфигурации поставщика — 242628

Ситуация: хранимая **конфигурация поставщика не соответствует** действительности — формально релиз совпадает с типовой (УТ 10.3), но в поддержке «висят» объекты отраслевого решения («БИТ: Управление автосервисом 8»), которых в типовой нет. При обновлении платформа предложит **удалить все объекты отраслевого решения**. Аналогичная беда после обновления БД через «Сравнить, объединить» без обновления конфигурации поставщика.

Рецепт (нужен cf-файл, соответствующий текущему релизу БД; релиз — «Справка → О программе»; перед началом — копия БД):
1. «Конфигурация → Поддержка → Настройки Поддержки» → **«Снять с поддержки»** → «Да» (желтая пиктограмма поддержки исчезает).
2. «Конфигурация → **Сравнить, объединить с конфигурацией из файла**» → на предложение поставить на поддержку — «Да»; **снять галочку с корневого узла** (чтобы не затереть свои изменения) → «Выполнить» → в правилах поддержки «ОК». Теперь поставщик соответствует БД.
3. Техническое хвост: изменённые объекты остались вне поддержки и при обновлении меняться не будут. «Конфигурация → Поддержка → Настройки поддержки» → «Сравнить, объединить» → снять все галочки, выделить нужный объект → «Изменить» → «Объект поставщика редактируется с сохранением поддержки» → «ОК» → «Выполнить» (флажок «Устанавливать для подчиненных объектов» — для веток целиком).

## 4. Инструменты

### 4.1. Проверка методов расширений — 2724437
Внешняя обработка: проверяет методы расширений с `&Вместо`, `&Перед`, `&После` и `&ИзменениеИКонтроль` после обновления типовой конфигурации. Смысл: после обновления типовой расхождения надо ловить до запуска пользователей, а не по жалобам.

### 4.2. Поиск заимствованных форм в расширениях — 2662713
Если в расширение скопирована форма, изменённая в новом релизе типовой, форму в расширении нужно обновить; инструмент находит такие заимствованные формы по всем расширениям. Смежное: forum9/topic305350 «Форма в расширяемой конфигурации изменена — надо ли обновлять?».

### 4.3. CF-Reader — 2685077
Чтение и объединение конфигураций **без Конфигуратора**: окно сравнения показывает две конфигурации (CF/CFE) одновременно; деревья A и B синхронизированы по группам; цветовая разметка (красный — только в A и т.д.). Полезен для быстрого анализа поставок/расширений.

## 5. Форумы

### 5.1. «Объект поставщика не редактируется» — forum83/topic143782
Автор (Anesk, 28.12.15): после обновления КА 1.3.67 объекты типовой нельзя править — «не редактируется»; хочется и обновляться, и дорабатывать.
Ответы (CaptainMorgan):
- признак «не редактируется» — правило поддержки; снять его на одиночный объект нельзя «навсегда» — это осознанное решение разработчика типовой;
- для правки: «Настройка поддержки» → «Включить возможность изменения»; тогда у изменённых объектов будет «редактируется с сохранением поддержки». Конкретно в теме совет: у **корневого узла** установить правило, разрешающее правку/добавление (см. Гайд 1 §5–6), при этом часть объектов останется «не редактируется» — их правило меняется через сравнение/объединение с конфигурацией поставщика.

### 5.2. «Не работает проверка применимости при &ИзменениеИКонтроль» — forum9/topic227698
Ключевой кейс (PythonJ, 13.10.19, платформа 8.3.15.1700):
- директива `&ИзменениеИКонтроль` работает, **пока** исходный метод совпадает с зафиксированным в расширении;
- если текст метода в типовой изменился, расширение **молчаливо откатывается** к оригинальному методу: ни Конфигуратор, ни «Предприятие» ничего не сообщают, расширение остаётся «подключенным» и проверку применимости проходит;
- по документации должно быть «Ошибка применения модуля … Текст модуля для метода … изменился» — не воспроизводится;
- практический вывод автора: поведение неотличимо от `&Вместо` — придётся при каждом обновлении сверять тексты вручную.
Ответы: у расширений много подобных дефектов («&После» не отрабатывает после проведения/отмены — AlexandrSmith); реквизиты «ненадёжные», формы при обновлении меняют параметры; процедуры целиком в расширение вставлять не стоит — сбои при изменении заменённой процедуры незаметны. Рекомендация stash_84 — заводить обращения в 1С (v8).
**Рабочий вывод для проекта**: после каждого обновления типовой прогонять проверку применимости и контроль методов (обработка §4.1); критичные доработки — через `&Перед`/`&После`/`&Вместо`, а не `&ИзменениеИКонтроль`.

### 5.3. «Диадок для самописной конфигурации» — forum9/topic303685
Автор (Arkadag, 23.09.23): модуль Диадока работает на УТ 11, нужен ограниченный функционал на самописной конфигурации; не может найти, где `Ядро.epf` проверяет текущую конфигурацию и запрещает работу.
Ответы:
- polax: включить отладку и пройти до вызова модуля УТ — это и будет место проверки;
- Arkadag (итог): в инструкции Контура по отладке встроенных обработок не хватало флага — **в «ТиповойМодульДиадок» (ТиповойМодульДиадок.epf / КонтурДиадокСтандартОФ для обычных форм) в функцию «ИнициализироватьПеременныеМодуля» пришлось дописать небольшой костыль**, т.к. глобальный флаг отладки в него не передаётся.
**Для проекта**: проверка конфигурации живёт в ядре модуля; путь адаптации — подключаемый модуль (ПМ) + включение режима отладки в системных настройках (см. Гайд 2 §7–8).

## 6. Перенос объектов из расширения в основную конфигурацию (массово, с рисками) — 1960294

«Инструкция по переносу объектов из расширения Cfe в основную конфигурацию Cf» (29.10.23, +69). Контекст автора: к конфигурации прикрутили 7 расширений — отладка невозможна, отчёты из Конфигуратора не собрать (часть объектов в разных расширениях). Мораль статьи: «за мнимым удобством расширений рождается калека» — и потому всё переносится обратно в конфигурацию.

**Готовим cfe (превращаем в cf):**
1. Выгрузить расширение в файлы.
2. Удалить из `Configuration.xml` те же 4 строки (см. §1.3).
3. Остальные файлы обработать через Total Commander / Notepad++: в выделенных группах папок (пример: Catalogs, Documents, Enums, DataProcessors, Constants, Reports, Roles…; **регистры — отдельно**: `//AccumulationRegisters` и `//InformationRegisters` исключены из обработки) заменить `<ObjectBelonging>Adopted</ObjectBelonging>` на пустую строку во всех файлах.
   - Ловушка: если у регистра сведений/накопления в расширении нет измерений — при применении изменений в пустой конфигурации будет ошибка, придётся переделывать.
4. Загрузить из файлов в пустую конфигурацию, сохранить cf. Если загрузка не прошла — устранить причину в расширении и повторить.

**Объединение с рабочей конфигурацией:**
1. Развернуть копию рабочей базы.
2. **УДАЛИТЬ РАСШИРЕНИЕ** из копии — иначе будут проблемы с применением объединения, придётся восстанавливать базу заново.
3. Объединить рабочую конфигурацию с конфигурацией из расширения; сверять справочники/документы/перечисления/реквизиты с исходниками. **Ловушка**: если не установить соответствие по всем заимствованным объектам, у реквизитов после объединения может оказаться тип «строка» — ошибка вылезет только в работе пользователей.
4. Проверить, что у документов на месте все регистры в движениях; добавить недостающие.
5. **Исправление текстов модулей**: в процедуре «ПередЗаписью» перенесённых документов должна быть строка `Если ОбменДанными.Загрузка Тогда Возврат; КонецЕсли;`. Если в расширении были «#Вместо»/«#Перед»/«#После» — проверить и удалить директиву **«ПродолжитьВызов»**. После объединения ещё раз пройти по модулям объектов расширения и перенести коды процедур («перед записью», «обработка проведения» и т.д.).
