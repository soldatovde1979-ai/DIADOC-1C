# План: автоматизация обновления модуля Контур.Диадок (УТ11)

> Версия: 2.0 · Дата: 07.10.2026 · Статус: согласован в чате 07.10, исполнение — после Шага 0.
> Основания: аудит плана v1 (07.10.2026, нумерация П-/Р-/У- — по нему), требования [docs/my-FT.md](my-FT.md),
> реестр [docs/Диадок_РеестрИзменений.md](Диадок_РеестрИзменений.md), факты по коду — [TZ-0 §1](tz/TZ-0-osushchestvimost.md).
> Изменения относительно v1 — в конце документа.

## 1. Постановка

**Что есть.** Модуль Контур.Диадок 4.61.1 для 1С:УТ11. Вендор поставляет его как **расширение конфигурации** `КонтурДиадок` (AddOn).
Наши доработки сделаны прямо внутри этого расширения: 12 вендорских файлов (около 167 участков, +2690/−111 строк),
плюс наша обработка `ДД_подключаемыйМодуль` (3699 строк), роль `шхДиадок` и изменённый режим совместимости.
Часть логики уже живёт в основной конфигурации: `т1кДиадокСервер`, регистр `т1кДиадок_НастройкиДоговоров` и др.

**Проблема.** Обновление на новую версию вендора — полный рабочий день ручного переноса и проверки.

**Цель.** 1 час (коридор до 1–1,5 ч) на обновление без потери функционала. Ошибка переноса ловится машиной.
Процесс воспроизводится по инструкции (my-FT Т-1…Т-5).

## 2. Идея решения

Вендор при обновлении заменяет своё расширение целиком. Значит, выигрыш даёт не «умный перенос» нашего кода,
а **уменьшение того, что приходится переносить**, и простой надёжный перенос остатка.

```
Слой 1. Наш код вне вендора        ПМ + тела наших процедур → основная конфигурация (модули т1кДиадок*)
Слой 2. Точки вызова в вендоре     1–3 строки «// ШХ <ID>» в нужных местах вендорских модулей и форм
Слой 3. Встроенная дельта          то, что не выносится (поз. 7, 8+13, 10, 11, 15 …) — минимально, с маркером ШХ
Слой 4. Метаданные расширения      роль шхДиадок, режим совместимости — как часть выгрузки
──────────────────────────────────────────────────────────────────────────────────────────────
Перенос слоёв 2–4                  git: ветка vendor (чистые выгрузки) → слияние в main
Проверки                           компиляция + инварианты + эталонные XML + короткий smoke
Регламент                          одна команда update.ps1 с журналом времени
```

**Формы — программно** (my-FT Т-11, Т-12). `Form.xml` вендора не трогаем. Наши реквизиты, элементы, команды
и обработчики добавляет код из основной конфигурации при создании формы. В модуле формы остаются только точки вызова
и универсальные диспетчеры событий. При обновлении форма вендора приходит как есть, а наш код её достраивает.

**Почему git, а не свой патчер.** Трёхстороннее слияние с контекстом обеих сторон, новые и удалённые файлы,
XML метаданных — всё это уже есть в git. Собственный SEARCH/REPLACE-патчер на JSON этого не умел (П2, П10, П11)
и требовал второго эталона (П3, П12).

конфигурации, полный дистрибутив, программное изменение форм), исполнение останавливается и план правится.

## 4. Распределение ИИ / человек

| Работа | ИИ | Человек |
|---|---|---|
| Сценарии проверок Шага 0 | Пишет | Выполняет на платформе, заполняет таблицу |
| Выгрузки в файлы / загрузка в ИБ | Готовит команды | Запускает (до появления update.ps1) |
| Код `.bsl` слоёв 1–3, правила проверок, скрипты | Пишет целиком | Ревью diff, загрузка в тестовую ИБ |
| Решения по поз. 5, 7, 8+13, 11 | Готовит варианты | Принимает |
| Smoke, приёмка | Готовит чек-лист | Выполняет |

Ограничение: тестовая ИБ и Конфигуратор — на стороне человека. Всё, что ИИ пишет в `.bsl`, считается непроверенным,
пока не прошло компиляцию и эталонные XML (П15).

## 6. Экономика (экспертная оценка, замеров нет)

**Одно обновление после внедрения:**

| Шаг регламента | Спокойный релиз | Релиз со сменой форматов / Ядра |
|---|---|---|
| Бэкап ИБ, сверка прода с последним релизом | 10 мин | 10 мин |
| Новый `.cfe` → служебная ИБ → выгрузка → коммит в `vendor` | 10–15 мин | 10–15 мин |
| Слияние, разбор конфликтов | 0–15 мин | 30–90 мин |
| Компиляция, инварианты, эталонные XML | 15–20 мин | 15–20 мин + разбор расхождений |
| Smoke (короткий: поведение покрыто эталонами) | 15–20 мин | 20–30 мин |
| Сборка `.cfe`, тег, журнал | 5–10 мин | 5–10 мин |
| **Итого** | **≈55–90 мин** | **≈1,5–3 ч** |

Цель 1–1,5 ч достижима в спокойный релиз при выполнении Шагов 2–6. На релизе, где вендор переписал места нашей дельты,
укладываемся в 1,5–3 ч, а не в «день».

**Разовая стоимость проекта:** Шаг 0 — 1–2 дня; Шаг 1 — 0,5–1; Шаг 2 — 2–3; Шаг 3 — 5–8 (основной объём —
≈1950 строк форм); Шаг 4 — 2–4; Шаги 5–7 — 2–3. **Итого ≈13–21 рабочий день.**
Окупаемость = разовая стоимость / (≈6 ч × число обновлений в год). При 6 обновлениях в год — около полугода–года.
⚠️ Частота релизов вендора неизвестна (my-FT, чулан Р1).

## 7. Как меряем успех

Единица везде — **точка дельты** (ID из табл. 3 реестра) или **шаг регламента**.

| Метрика | Цель | Источник |
|---|---|---|
| Время обновления, сумма по шагам | ≤ 1–1,5 ч в спокойный релиз | журнал `update.ps1` |
| Точки дельты, перенесённые слиянием без ручной правки | ≥ 90% | отчёт инвариантов |
| Конфликты, требующие разработчика | ≤ 3 точки | отчёт слияния |
| Расхождения эталонных XML, не объяснённые вендором | 0 | отчёт проверок |
| Ошибки, найденные после ввода в прод | 0 | журнал (поле «где найдено») |
| Ошибок компиляции после сборки | 0 | проверка модулей |

Приёмка — на 2–3 обновлениях с пометкой типа релиза (TZ-7): одно спокойное обновление ничего не доказывает.
Базу «8 ч» замеряем по шагам на ближайшем обновлении по старой схеме, если оно случится раньше ввода.

## 8. Что проверки НЕ ловят (явно, чтобы не было ложного доверия — Р8)

- Логические ошибки в сценариях, не покрытых эталонными XML и smoke.
- Изменения поведения на стороне сервиса Диадок (API, форматы приёма).
- Права пользователей в прод-ИБ, если тестовая ИБ отличается по ролям.
- Визуальную раскладку программно созданных элементов форм (проверяется только в smoke).

## 10. Изменения относительно v1

- Убраны: Baseline-Исходный и Baseline-Целевой, нормализация всех 205 блоков, JSON-реестр патчей, патчер на OneScript,
  тесты T2/T3 по MD5 и счётчикам, «самоаудит» (П3, П4, П6, П11, П12, У8, У15).
- Шаг «заимствование форм в расширение» заменён программным изменением форм из основной конфигурации
  (П1 подтверждён фактом Ф1: модуль вендора сам является расширением).
- Добавлены: Шаг 0, ретро-прогон, эталоны поведения до рефакторинга, сигнатурный контроль и правила групп,
  сверка прода, бэкап, откат, автообновление, честная экономика и разовая стоимость.
- Метрики приведены к одной единице (точка дельты).
