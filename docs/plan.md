# План действий: автоматизация обновления модуля Контур.Диадок

## Исходная постановка (что я хочу)

**Что есть.** Модуль Контур.Диадок для 1С (УТ11), кастомизированный под нас: доработки заполнения документов и выгрузки, размеченные в коде комментарием ШХ (205 блоков в 12+ файлах, 23 позиции по реестру).

**Проблема.** При выходе новой версии вендора обновление занимает **полный рабочий день**: вручную переношу свои доработки в обновлённый код вендора, затем проверяю, что ничего не потерялось и не сломалось.

**Что хочу.** Сократить время обновления на новую версию вендора до **1 часа** (допустимый коридор — до 1–1,5 часа).

**Ограничения и условия:**

1. Доработки никуда не деваются — весь текущий функционал сохраняется.
2. Кастомизации не «вшиваются» в код вендора напрямую, а живут там, где вендор их переживёт обновление.
3. Перенос доработок на новую версию должен быть проверяемым: ошибка переноса ловится автоматически, а не пользователем на боевом экземпляре.
4. Процесс должен воспроизводиться без знания истории проекта — по инструкции.
5. Часть работ выполняет ИИ, часть — человек; распределение зафиксировано в плане.

**Как меряем успех.** Контрольное обновление на очередной версии вендора по секундомеру: суммарное время ≤1–1,5 ч, автоматический перенос ≥90% правок, ручных конфликтов ≤3, регрессия по smoke-списку = 0.

---

> Основание: реестр кастомизаций [docs/Диадок_РеестрИзменений.md](Диадок_РеестрИзменений.md) (23 позиции, база — чистый дистрибутив вендора `SRC/TypeDiadok`, версия 4.61.1).
> Статус: план согласуется. Код не правится до подтверждения.

## Архитектура целевого решения

```
Чистый дистрибутив вендора (.cfe)
        │
        ▼
[Скрипт-патчер tools/patcher]  ◄── Реестр патчей (якорь = функция вендора + SEARCH/REPLACE)
        │
        ▼
Патченная выгрузка + отчёт о конфликтах
        │
        ▼
[Тест-скрипт tools/tests] — сверка с эталоном (MD5 модулей, полнота ШХ-блоков, smoke-лист)
        │
        ▼
Загрузка в конфигурацию + расширение (формы) → smoke-тест → релиз
```

## Шаг 1. Два слепка: исходный и целевой

Фиксируются **два** эталона:

1. **Baseline-Исходный** — копия текущей выгрузки → `SRC/Baseline-Исходный/` + MD5-манифест.
   «Фотография того, что есть сейчас» — контроль «ничего не потеряли по пути».
2. **Baseline-Целевой** — слепок того, к чему идём. ИИ знает, куда каждый блок уйдёт
   (реестр кастомизаций + ТЗ), поэтому **сразу эмулирует конечное состояние**: создаёт копию
   выгрузки, в которой уже выполнены нормализация разметки, перенос в хуки и вставки патчей,
   как если бы скрипты отработали. → `SRC/Baseline-Целевой/`.
   Это «фотография цели» — то, что патчер обязан воспроизводить на чистом дистрибутиве.

Ограничение: Baseline-Целевой покрывает **текстовую часть** (модули `.bsl`, реестр патчей).
Заимствованные формы и рег. задание (Шаг 3) создаются в Конфигураторе и проверяются
smoke-тестом — их в слепок не включить.

> **Правило расхождений.** Если выход скриптов ≠ Baseline-Целевому — разбираем и решаем,
> где ошибка: в скрипте (эталон соответствует замыслу — чиним скрипт) или в эталоне
> (при симуляции допустили расхождение с замыслом реестра — правим эталон). Решение
> фиксируется, причина расхождения устраняется в источнике.

> **Зачем исходный слепок, если состав кода меняется?** Он сверяется не целиком, а по
> контролируемым величинам: код внутри каждого перенесённого ШХ-блока — байт-в-байт,
> число блоков 205 → 205, состав объектов конфигурации не убыл молча.

## Шаг 2. Нормализация разметки
- Все 205 блоков `ШХ` приводятся к единому виду `// ШХ <ID> BEGIN ... // ШХ <ID> END`, каждому присваивается ID из реестра.
- Проверка: количество блоков до/после совпадает, код внутри — байт-в-байт.

## Шаг 3. Вынос в расширение (позиции 17–21 реестра)
- Заимствованные формы `ФормаЭлементаСправочника`, `ФормаУправляемая`, `НастройкаПечатныхФорм`, `Настройки`, `ФормаПакета` → расширение (`&Вместо`/`&После`).
- Роль `шхДиадок`, рег. задание «Автоматизация ЭДО», макет `т1кПечатьСверкиДиадок` → расширение.
- Из модулей вендора перенесённые блоки удаляются.
- Результат: ~60% правок больше не живут в коде вендора.

## Шаг 4. Перенос в хуки (позиции 1, 2, 9, 14, 16, 23)
- Логика из веток Ядра/ХранениеДанных → официальные события `ДД_подключаемыйМодуль`:
  `ПодготовитьПакет`, `ПодготовитьЭлектронныйДокумент`, `ПодготовитьЭлектронныйДокументПоВнешнейПечатнойФорме` и др.

## Шаг 5. Реестр патчей (позиции 4–8, 10–13, 15)
- Невыносимое (сквозной `Договор1С` в Ядре/ХранениеДанных, `НаимЕдИзм` в ГенерацияXML, контракты, `РежимПользователя`)
  → `tools/patcher/registry/`: якорь (имя функции вендора + уникальный контекст) + SEARCH/REPLACE.
- Для каждой группы — счётчик вставок для контроля.

## Шаг 6. Скрипт-патчер
- `tools/patcher` (OneScript): вход — чистая выгрузка вендора, выход — патченная выгрузка + отчёт
  (`применено N / конфликт M`, поимённый список). Конфликты скрипт не правит — только фиксирует.

## Шаг 7. Тест-скрипт
- Прогон: `SRC/TypeDiadok` (чистый дистрибутив) → патчер → сверка с Baseline-Целевым:
  MD5 каждого модуля, полнота всех ШХ-блоков, smoke-список ключевых функций.
- Зелёный прогон = патчер воспроизводит целевой слепок без участия человека.
- Расхождение = сигнал по правилу Шага 1: ошибка в скрипте или в целевом слепке — решаем, что править.

## Шаг 8. Документация
- `docs/update-checklist.md`: пошаговый регламент обновления (загрузка → патчер → тест → сборка → smoke)
  + правила ведения реестра патчей (новая доработка = сразу патч в реестре, не «вшивается» в модуль).

## Шаг 9. Приёмка
- Контрольное обновление на очередной версии вендора, замер времени по шагам (цель ≤ 1–1,5 ч),
  фиксация результата; эталон пересобирается и фиксируется.

## Порядок исполнения: что делает ИИ, что человек

> Правило: ИИ правит только текстовые файлы (`.bsl`, `.xml`, `.md`, `.json`, `.os`).
> Всё, что создаётся через Конфигуратор 1С (формы, роли, макеты как объекты), — делает человек по подготовленному ИИ материалу.

| Шаг | Что делает ИИ | Что делает человек | Можно ли отдать ИИ целиком |
|---|---|---|---|
| 1. Эталон (ТЗ-1) | Копирует выгрузку в `SRC/Baseline-Исходный/`, создаёт `manifest.md5` и `baseline.json` | Контрольный просмотр манифеста | Да |
| 2. Нормализация (ТЗ-2) | Правит комментарии ШХ по файлам, сверяет суммы блоков до/после | Просмотр diff | Да |
| 3. Расширение (ТЗ-3) | Готовит код обработчиков (`&Вместо`/`&После`) и шапки заимствованных форм | Заимствование форм/рег. задания/макета в Конфигураторе + вставка кода | Нет: формы — бинарные артефакты Конфигуратора |
| 4. Хуки (ТЗ-4) | Переносит логику в `ДД_подключаемыйМодуль`, чистит ветвления в модулях вендора | Smoke-тест в базе | Да |
| 5. Реестр патчей (ТЗ-5) | Составляет JSON-патчи сравнением эталона с чистым дистрибутивом | Ревью реестра | Да |
| 6. Патчер (ТЗ-6) | Пишет скрипт целиком | Ставит OneScript, запускает | Да |
| 7. Тесты (ТЗ-7) | Пишет тест-скрипт, чинит по результатам | Запускает, смотрит протокол | Да |
| 8–9. Регламент, приёмка | Пишет документы, помогает разбирать конфликты | Проводят контрольное обновление, утверждают | Регламент — да; приёмка — человек |

Порядок жёсткий: **Шаг 1 обязателен до любых правок** (нечем сверять — ничего не трогаем). Шаги 5–7 выполняются только после 2–4: реестр патчей фиксирует остаток, который не ушёл в расширение и хуки.

### В. Итоговое состояние — как выглядит «после»

1. **Код вендора чистый**: модули вендора отличаются от дистрибутива только ~40 точками,
   каждая описана патчем в реестре. Формы вендора не правятся вовсе.
2. **Вся наша логика в трёх местах**: расширение (формы, рег. задание), хук

3. **Обновление вендора — конвейер**: загрузили новую версию → запустили патчер →
   тесты зелёные → собрали. Руки человека — только на конфликтах (штатно ≤3 позиций).

## Риски

| Риск | Митигация |
|---|---|
| Вендор меняет код в месте якоря → конфликт патча | Отчёт конфликтов; Шаг 4 минимизирует точки; критичные места — хуками |
| `&Вместо` в расширении отстанет от логики вендора | Smoke-проверка формирования XML в тест-скрипте |
| Потеря кода при нормализации разметки | Сверка суммы блоков до/после с эталоном |
| «Мусорные» блоки-комментарии в реестре | Классификация каждого блока на Шаге 2 |

## Аудит плана (самопроверка направления)

### Что в плане сделано правильно
1. Идём через официальный механизм расширения вендора (`ДД_подключаемыйМодуль` + события) — это единственный вендоронезависимый слой.
2. Эталон + тест-скрипт (ТЗ-1, ТЗ-7) замыкают цикл: любая ошибка переноса ловится машиной, а не пользователем.
3. Трассировка «позиция реестра → патч/форма/хук» — ничего не теряется молча.
