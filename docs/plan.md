## 1. Задача

**Что есть.** В проде — «1С:ERP. Управление холдингом» 3.1.9.4 на платформе 8.3.27 [скриншот]. Модуль Контур.Диадок 4.61.1 стоит как **расширение** — так 1С называет надстройку, которая подключается к конфигурации поверх и меняет её поведение, не трогая саму конфигурацию. Это расширение прислал вендор (СКБ Контур). Наши доработки вписаны прямо в его код: **26 позиций реестра** (позиция — одна доработка с понятной целью, см. [реестр](Диадок_РеестрИзменений.md)), 178 мест в 14 файлах вендора (R1).

**Проблема.** Вендор при обновлении заменяет своё расширение целиком. Наши 178 мест приходится каждый раз переносить руками. Сейчас обновление занимает **3 рабочих дня** (my-FT Р-6), а обновляться нужно минимум 4 раза в год (Т-17).

**Цель.** Обновление за 1 час, допустимо до 1,5 ч (Т-1). Функциональность сохраняется полностью (Т-2). Ошибка переноса ловится автоматически, а не пользователями (Т-4). Обновление делает стажёр по инструкции (Т-5, Т-18).

## 2. Что получится в итоге

В проде будет три слоя:

| Слой | Что в нём | Кто меняет | Что с ним при обновлении вендора |
|---|---|---|---|
| **Поставка модуля Диадок** | Код вендора без единой нашей строки. Лежит в основной конфигурации как **поставщик на поддержке** (см. ниже) | Только вендор | Заменяется целиком новой версией, автоматически |
| **Наш код в основной конфигурации** | Наш подключаемый модуль, модули `т1к*`, регистры настроек — всё, что содержит нашу логику | Мы | Не трогается |
| **Наше расширение `ДиадокДоработки`** | Только «зацепки» за код вендора: в нужном месте вызвать наш код; создать наши поля на формах вендора | Мы | Проверяется: все ли зацепки сработали на новой версии. Если нет — это и есть конфликт, его разбирает человек |

**Поставщик на поддержке.** В 1С конфигурацию можно «поставить на поддержку» поставщика: его объекты помечаются как его, и потом их можно обновить из нового файла поставщика одной командой. Поставщиков может быть несколько, и обновление одного не трогает объекты других (S001:L78-L79). В нашем проде так уже живут не меньше шести поставщиков: 1С, «Диадок» (подсистема хранения Контура, версия 2.25), EAM, Kafka и другие [скриншот]. Модуль Диадок станет ещё одним.

**Почему именно так.** Наш слой «зацепок» должен ссылаться на код вендора. Расширение не может зацепиться за объекты другого расширения (форумы — [указатель Q11](research/00_UKAZATEL.md); официального текста нет — проверка П7 на шаге 0). Поэтому код вендора переезжает из расширения в основную конфигурацию — тогда наше расширение «видит» его штатно (R7 v2 §3.1).

**Как будет выглядеть обновление** (подробно — шаг 6):

1. Скачать новый файл модуля у Контура.
2. Запустить одну команду `update.ps1` на тестовой копии прода. Она сама:
   - перепаковывает модуль из формата «расширение» в формат «поставка»;
   - обновляет им конфигурацию;
   - загружает наше расширение;
   - прогоняет проверки.
3. Прочитать отчёт. В нём только конфликты — места, где вендор поменял код, за который мы цепляемся.
4. Если конфликтов нет и проверки зелёные — перенести в прод.

## 3. Шаги

Порядок — сначала снимаем риски, потом переносим (Т-29). Шаги 0 и 1 ничего не меняют в проде и в коде: они проверяют и фиксируют. До конца шага 7 прод работает как сейчас — всё делается на **тестовой базе** (копия прода, Т-14).

Кто делает: **ИИ** — пишет код, скрипты и документы в репозитории. **Архитектор** и **стажёр** — люди: запускают 1С, загружают, проверяют, решают.

### Шаг 2. Сборка поставки модуля и постановка на поддержку

| | |
|---|---|
| **Вход** | Поставка 4.61.1 из `SRC/TypeDiadok` — та же версия, что в проде: переезд отделён от обновления, эталоны «до» и «после» должны совпасть. Скрипт перепаковки после шага 0 |
| **Выход** | Файл `Диадок-модуль.cf` в git. Тестовая база, где модуль стоит поставщиком на поддержке, а расширение вендора удалено. Карта UUID в git |
| **Зачем** | Перевести код вендора в слой «поставка», чтобы за него могло цепляться наше расширение и чтобы его можно было обновлять одной командой |
| **Что делаем** | 1. Скрипт перепаковывает `.cfe` → `.cf` (ниже). 2. В тестовой базе: удалить расширение вендора, затем объединить конфигурацию с `Диадок-модуль.cf` с постановкой на поддержку (`/MergeCfg -EnableSupport`, S008:L2306-L2312), сохранить файл настроек объединения. 3. Проверить, что база запускается |
| **Что закрывает** | Т-33, Т-8 |
| **Кто** | ИИ — скрипт; архитектор — запуск |
| **Стоимость** | 3,5 ч человека, 3 ч ИИ |

**Перепаковка (конвертация) `.cfe` → `.cf`.** Вендор даёт модуль только как расширение. Поставщик на поддержке должен быть обычным файлом конфигурации `.cf`. Платформа сама так не умеет, но преобразование механическое (S075:L43-L62, S003:L109-L121):

1. Выгрузить расширение в XML-файлы.
2. Убрать 4 служебные строки «это расширение» в `Configuration.xml` и пометки `Adopted` во всех файлах.
3. Загрузить в пустую базу и сохранить как `.cf`.

Нашей логики в скрипте нет — только смена упаковки. Ловушки из статей (картинки, заимствованные формы, регистры) к нам не относятся: модуль ничего не заимствует из конфигурации, кроме языка [код].

Ещё две правки делает тот же скрипт:
- **Пустой корень.** **Корень конфигурации** — общие свойства и модули всей конфигурации (модуль сеанса, командный интерфейс). Его делят все поставщики, поэтому любые правки в нём конфликтуют при каждом обновлении (S001:L81). Вендор трогает корень в двух местах [код] — эти два места скрипт выбрасывает, а наше расширение делает то же самое у себя (шаг 4). В итоге поставка модуля содержит только собственные объекты вендора [вывод, П3].
- **Карта UUID.** У каждого объекта 1С есть внутренний номер — **UUID**. По нему 1С при обновлении узнаёт «это тот же объект». У разных сборок вендора одной версии UUID разные (ТЗ-0 v3 Ф18). Если номер «поплывёт» между релизами, 1С решит, что объект удалён и создан заново. Для обработок это безвредно, а для роли — нет: слетят назначения пользователям. Скрипт держит в git таблицу «имя объекта → UUID» и проставляет номера по ней [вывод, П2]. А наше расширение сопоставляет заимствованные объекты **по именам**, а не по UUID (ТЗ-4 §3.1) — так оно не зависит от UUID вовсе.

### Шаг 3. Наш код — в основную конфигурацию

| | |
|---|---|
| **Вход** | Тестовая база после шага 2. Наш код из расширения прода (`SRC/ERPDiadok`) |
| **Выход** | В основной конфигурации: наш подключаемый модуль, наши процедуры в общих модулях `т1кДиадок*`, роль. Часть доработок переведена на официальные события вендора |
| **Зачем** | Наш код должен жить там, где обновление вендора его не трогает (Т-3, Т-7) |
| **Что делаем** | По таблице раздела 4: строки с действием «ПМ в конфигурацию», «тело в наш модуль», «событие ПМ», «роль» |
| **Что закрывает** | Т-3, Т-7, часть Т-2 |
| **Кто** | ИИ — код; архитектор — загрузка, проверка эталонами |
| **Стоимость** | 12 ч человека, 20 ч ИИ |

**Подключаемый модуль (ПМ)** — официальный способ вендора дорабатывать модуль без правки его кода. Это наша обработка с функцией `ОбработатьСобытие`. Модуль вендора вызывает её в определённые моменты — при **событиях**: «пакет подготовлен», «нужна печатная форма», «найти сопоставление номенклатуры» и т. д. (S011:L93-L109, 28 событий — R3). Где лежит ПМ, задаётся в настройках модуля; вариант «в конфигурации» вендор поддерживает [код, ТЗ-0 v3 Ф2]. Сейчас наш ПМ лежит внутри расширения вендора — переносим в основную конфигурацию как есть.

**Событие вместо зацепки.** Если доработку можно сделать через событие ПМ, это лучший вариант: вендор сам гарантирует, что событие будет вызвано, и при обновлении ломаться нечему. Кандидаты — в колонке «Событие ПМ» раздела 4.

### Шаг 4. Наше расширение: зацепки и формы программно

| | |
|---|---|
| **Вход** | Тестовая база после шага 3. Таблица раздела 4 |
| **Выход** | Расширение `ДиадокДоработки` в git: зацепки за методы вендора и программное создание наших полей на пяти формах вендора. Эталоны X1–X7 совпадают с шагом 1, smoke пройден |
| **Зачем** | То, что нельзя сделать событием ПМ, делаем зацепками — без единой строки в коде вендора (Т-3) |
| **Что делаем** | По таблице раздела 4: строки с действием «зацепка» и «форма программно». Плюс модуль сеанса и командный интерфейс вместо вендорских (шаг 2, «пустой корень») |
| **Что закрывает** | Т-2, Т-3, Т-11, Т-12 |
| **Кто** | ИИ — код; архитектор — загрузка, эталоны, smoke |
| **Стоимость** | 28 ч человека, 55 ч ИИ |

**Зацепка** — метод нашего расширения, который 1С вызывает вместо метода вендора или рядом с ним. Вид зацепки задаёт **аннотация** — строка над методом:

| Аннотация | Что делает | Когда берём |
|---|---|---|
| `&Перед("Метод")` / `&После("Метод")` | наш код выполняется до или после метода вендора, сам метод не меняется | когда достаточно добавить действие. Только для процедур — для функций нельзя (S006:L2091-L2109) |
| `&ИзменениеИКонтроль("Метод")` | копия метода вендора с нашими вставками `#Вставка … #КонецВставки`; 1С следит, чтобы остальной текст совпадал с вендорским | когда нужно вклиниться в середину метода. На один метод — одна такая зацепка (S006:L1985-L1995) |

**Проверка применимости** — 1С при загрузке расширения проверяет, что каждая зацепка «села» на свой метод. Если вендор поменял метод, проверка выдаёт ошибку: «текст метода изменился» (S006:L1853-L1873). Это и есть автоматический сигнал конфликта (Т-4). Есть форумное свидетельство, что на старой платформе (8.3.15) ошибки не было и зацепка молча отключалась (S003:L90-L96) — проверяем на нашей 8.3.27 (П8). Поэтому есть и вторая защита: скрипт сам сравнивает старый и новый текст каждого метода, за который мы цепляемся (шаг 5).

**Формы программно (Т-11).** Это главное отличие от прежних попыток. На формы вендора ничего не рисуем мышкой. Вместо этого наше расширение «заимствует» форму и в момент её открытия кодом создаёт наши поля, кнопки и обработчики.

**Заимствовать** — взять объект вендора в своё расширение, чтобы цепляться за его методы. У формы при этом заимствуются только элементы, реквизиты и команды добавляются кодом (S006:L2395-L2409; приёмы — S067:L145-L162, S070:L132-L141).

Пример — позиция 17, основная форма модуля:

| | Было (сейчас) | Стало |
|---|---|---|
| Файл формы вендора `Form.xml` | наши поля `шхРежимПодписания` и др. вписаны прямо в файл вендора (ТЗ-0 v3 Ф10) | файл вендора не тронут — он вообще в поставке, править его нельзя |
| Модуль формы вендора | наши процедуры с пометкой `ШХ` вписаны в модуль | не тронут |
| Наше расширение | — | у заимствованной формы одна зацепка `&После("ПриСозданииНаСервере")`. Внутри одна строка: вызвать `т1кДиадокФормы.ДополнитьОсновнуюФорму(ЭтаФорма)` |
| Наш модуль `т1кДиадокФормы` (основная конфигурация) | — | процедура создаёт наши поля и кнопки кодом (`Элементы.Добавить`, `Команды.Добавить`) и навешивает обработчики |

При обновлении вендора: если он не переименовал элементы, рядом с которыми мы вставляем свои, всё работает как было. Если переименовал — `т1кДиадокФормы` выдаст понятную ошибку на тестовой базе, а не у пользователя.

Пример — зацепка в методе, позиция 14 (хранение в прикреплённых файлах):

## 4. Что делаем с каждой доработкой (26 позиций реестра)

**Действия:**
- **ПМ в конфигурацию** — наш подключаемый модуль переезжает из расширения вендора в основную конфигурацию без изменений кода.
- **Событие ПМ** — доработка делается в нашем ПМ на официальном событии вендора, зацепка не нужна. Проверяется на шаге 0 (П13) или по эталону.
- **Тело в наш модуль** — наша процедура переезжает в общий модуль основной конфигурации; в расширении остаётся зацепка из одной строки вызова.
- **Зацепка** — `&После` / `&Перед` / `&ИзменениеИКонтроль` в нашем расширении.
- **Форма программно** — см. шаг 4.

### 6.4. Окупаемость

- Сейчас: 4 обновления × 3 дня = 12 дней ≈ 96 ч архитектора в год (Р-6).
- После: 4 × 1,5 ч стажёра + оценочно 4 × 1 ч архитектора на конфликты ≈ 10 ч в год.
- Экономия ≈ 86 ч в год. Проект — 109 ч людей. **Окупаемость ≈ 1,3 года** по часам людей.

Если замер на шаге 8 покажет, что старое обновление занимало меньше 3 дней, окупаемость растёт пропорционально. Тогда проект оправдывают ещё и Т-4 (ошибки ловит машина) и Т-18 (обновляет стажёр).

## 7. Чистый дистрибутив вендора (Т-23)

**Что это.** Модуль ровно в том виде, как его прислал Контур, без наших правок. Для каждого релиза это:
1. файл `diadoc_um.cfe`;
2. его выгрузка в XML-файлы;
3. собранный из него `Диадок-модуль.cf`.

**Зачем нужен.**
1. Из него собирается поставка (шаг 2).
2. По двум соседним релизам скрипт видит, какие методы вендор поменял, и сверяет их с нашими зацепками (шаг 5).
3. Из него восстанавливается прод, если нужно откатиться.

**Где живёт.** В git, в отдельной папке поставки, по одному коммиту на релиз с меткой версии. Точное имя папки задаёт ТЗ шага 2. Старые релизы не стираем: они нужны для сравнения и отката, а места в git занимают немного (меняются только изменённые файлы).

**Что с `SRC/TypeDiadok`.** Это чистая 4.61.1, но **другой сборки**, чем в проде: UUID не совпадают (ТЗ-0 v3 Ф18). Она нужна один раз: из неё собирается поставка 4.61.1 для перехода прода (шаг 2) — старых версий Контур не отдаёт. После шага 2 её содержимое лежит в истории `SRC/postavka`; тогда предложим перенести папку в архив. Удаляем только с вашего согласия.

**Что с `SRC/ERPDiadok`.** Это выгрузка прода с нашими правками внутри — источник переноса на шагах 3–4 и описи R1. Хранится до приёмки (шаг 8), потом — в архив.

## 8. Риски

| Риск | Чем закрыт |
|---|---|
| Ключевая гипотеза не подтвердится | Шаг 0 до вложений; условие выхода — план v3 |
| Зацепка молча отключится при изменении метода вендора | П8; независимое сравнение текстов перехваченных методов (шаг 5) |
| Вендор переименует элементы формы, рядом с которыми мы вставляем свои | Ошибка на тестовой базе при открытии формы; smoke |
| Вендор выпустит функцию, которая работает только в варианте «расширение» | Контур.Интеграция не нужна (Т-34). Новые такие функции отслеживаем по «Новое в модуле» при каждом обновлении |
| Поддержка Контура откажет с доработанным модулем | Так и сейчас («Оставить заявку», S002:L83). Поставка у нас без правок — её можно показать как типовую |
| При переходе прода слетят назначения ролей | Выписать назначения до перехода и восстановить (шаг 7) |
| Скрипт сломается — стажёр застрянет | Запасной путь руками (шаг 6, Т-32) |

**Что проверки не ловят.** Изменение поведения, не покрытое эталонами X1–X7 и smoke. Пример: вендор поменял логику в методе, за который мы не цепляемся, и это бьёт по нашей доработке косвенно. Защита — расширять эталоны, когда такое случится, и не уменьшать smoke.
